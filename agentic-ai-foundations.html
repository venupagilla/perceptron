01 · Introduction to AI Agents

What is an AI agent?

The shift from software that answers to software that acts.

The core definition

An AI agent is an autonomous software entity designed to perceive its environment, reason through problems, make decisions, and execute actions to achieve a specific, human-directed goal. Unlike traditional software that relies on rigid, hard-coded rules, an AI agent uses an LLM as its "brain" to dynamically navigate unpredictable situations.

Standalone LLMs vs. AI agents

A major shift in how we interact with AI: from a reactive input/output tool to a proactive, goal-directed system.

FeatureStandalone LLM (Traditional GenAI)AI Agent (Agentic AI)
Interaction modelInput/output (reactive) — waits for a prompt, generates text, stops.Goal-directed (proactive) — works continuously toward a broader objective with minimal oversight.
ExecutionJust generates content; cannot take real-world action.Can execute actions via APIs, tools, databases, external software.
WorkflowLinear and static.Iterative loop — continuously evaluates its own progress and self-corrects.
01 · Introduction to AI Agents

The agentic loop

Every AI agent operates within a continuous feedback loop that mirrors human initiative.

graph LR A[Perceive] --> B[Reason / Plan] B --> C[Act] C --> D[Evaluate & Self-Correct] D -->|adjust plan| B D -->|goal met| E[Done]

1 · Perceive

Gathers information from its environment — user prompts, database records, system logs, or external APIs.

2 · Reason / Plan

Decomposes a large, complex goal into smaller sub-tasks, deciding how to approach it using patterns like Chain-of-Thought.

3 · Act

Executes commands using external tools — querying a SQL database, calculating math, or sending an email.

4 · Evaluate & self-correct

Analyzes the output of its action. If the result didn't solve the problem, it adjusts its plan and retries autonomously.

01 · Introduction to AI Agents

Core components

An AI agent is more than just an LLM — it's a system built out of four parts that work together to execute complex workflows.

1

The Core (the brain / LLM)

Role: the central decision-maker and reasoning engine. It processes the request, parses incoming data, decides which actions to take, and interprets results. Rather than just generating static text, it acts as a runtime engine that routes logic dynamically.

2

Memory

Split into two types: short-term memory retains the in-progress context of the current task loop (what the user said a few prompts ago); long-term memory retains information across sessions, often via vector databases, to recall past behavior, preferences, or organizational knowledge over weeks or months.

3

Tools (the capabilities)

How the agent interacts with the outside world — web search APIs, database connectors, code execution environments. The Core LLM never executes a tool itself; it generates a structured command (a JSON payload) declaring which tool to run and with what arguments.

4

Planning & reasoning loop

The architectural structure dictating how the agent breaks down tasks. Rather than guessing an answer immediately, the loop forces the agent to write a plan, execute a step, look at the result, and decide the next step dynamically.

01 · Introduction to AI Agents

Reasoning patterns

The cognitive frameworks that let an agent think, plan, and decide what to do next — instead of rushing a single, immediate response.

1Chain-of-Thought (CoT)

The agent breaks a complex problem into a linear sequence of intermediate steps before arriving at a final answer — mimicking human "thinking out loud." Given a complex math or logic question, it writes out Step 1, Step 2, Step 3 sequentially. This drastically improves accuracy on multi-step problems by preventing the LLM from rushing to an incorrect conclusion.

graph LR Q[Question] --> S1[Step 1] S1 --> S2[Step 2] S2 --> S3[Step 3] S3 --> A[Final Answer]

2ReAct (Reason + Act)

Combines reasoning (thinking about what to do) with acting (using external tools) in a strict, repeating cycle.

graph LR A[Thought] --> B[Action] B --> C[Observation] C --> A

Thought

"I need to find the current stock price of Oracle."

Action

Calls a stock market API tool.

Observation

Receives the live price data from the API.

This lets the agent dynamically interact with the real world, evaluate the results of its actions, and alter its plan based on new data.

3Tree-of-Thoughts (ToT)

An advanced framework where the agent explores multiple alternative reasoning paths simultaneously, rather than a single linear chain: it generates a "tree" of potential steps (branches), evaluates each one for likelihood of success, and backtracks if a branch hits a dead end. Ideal for strategic planning, chess, or deep debugging where multiple solutions exist.

graph TD R[Root Problem] --> B1[Branch A] R --> B2[Branch B] R --> B3[Branch C] B1 --> B1a[Dead end] B2 --> B2a[Promising] --> S[Solution] B3 --> B3a[Backtrack] --> R

Quick comparison

PatternWorkflow typeBest used for
Chain-of-ThoughtLinear / internalStep-by-step logic and mathematical reasoning.
ReActIterative / externalTasks requiring real-time data lookup and tool execution.
Tree-of-ThoughtsBranching / evaluativeComplex problems requiring exploration, optimization, and backtracking.

Framework & implementation

Agent frameworks overview

LangChain & LangGraph

LangChain is the most widely adopted framework — it handles chaining LLM calls. LangGraph adds stateful, graph-based workflows.

Strengths: huge ecosystem, tons of integrations, great documentation.
Weaknesses: can be overengineered for simple tasks; abstractions add complexity.
Best for: production teams needing orchestration, state management, middleware, testing.

OpenAI Agents SDK

A newer, structured approach using the Responses API and native tool orchestration. Supports agents, tools, guardrails, multi-agent workflows.

Strengths: tight OpenAI integration, built-in observability, less boilerplate.
Weaknesses: more opinionated, less flexible than LangGraph, evolving ecosystem.

Other frameworks (not covered in depth)

CrewAI — popular for team-structured workflows. Hugging Face SmolAgent — good for learning, with a small code footprint.

Practical guidance: start simple for learning; use frameworks (LangChain / LangGraph / OpenAI SDK) for production as complexity grows.

Creating & invoking the agent

python

Agent in action — three examples

Single tool call

"What is 42 + 58?" → agent identifies need for addition → calls Add once → returns result. Loops needed: 1

Sequential tool calls

"What is 15 × 8 ÷ 3?" → Loop 1: multiply 15×8=120 → Loop 2: divide 120÷3=40. The agent figures out order automatically.

Multi-step reasoning

"Rectangle 12×7 — area and its square root?" → Loop 1: multiply → 84 (area) → Loop 2: square root of 84. It derived "area = width × height" on its own and chained the results.

What makes it an "agent"?

  • No predefined workflow — the agent figures out the sequence
  • Dynamic reasoning — decides which tools to call and when
  • Automatic chaining — passes results between tool calls
  • Self-directed — plans strategy without explicit programming

Why safety matters

Key insight: agents are more powerful than chatbots, and therefore more dangerous when things go wrong. Every team building agents must understand these risks.

Real-world agent attacks (2024)

August 2024 · Prompt Injection

Slack AI data exfiltration

  1. Attacker posted hidden instructions in a public Slack channel
  2. When users queried Slack AI, it pulled data from private channels
  3. Data (including API keys) was embedded in a phishing link
  4. Secrets were exfiltrated to the attacker
September 2024 · Memory Poisoning

ChatGPT memory "SpAIware"

  1. Malicious instructions injected into ChatGPT's persistent memory via a crafted document
  2. Poisoned memory persisted across all future sessions
  3. Data was silently exfiltrated to an external server
Why these matter: both attacks demonstrate the critical need for a layered defense architecture.

1

Input validation (pre-LLM)

Sanitize and validate all incoming data before it reaches the LLM: treat all external content as untrusted, enforce a tool allow-list, run permission checks, classify risk level (low/medium/high → route accordingly), detect & redact PII.

python 
def validate_input(user_input):
    # 1. Check for injection patterns
    if "ignore previous" in user_input.lower():
        return "BLOCKED: Potential prompt injection"

    # 2. Redact PII
    user_input = redact_pii(user_input)

    # 3. Classify risk
    risk_level = classify_risk(user_input)

    return {"processed_input": user_input, "risk": risk_level}
2

LLM guardrails (during processing)

Control LLM behavior during processing: explicit boundaries in the system prompt, tool access controls, treating retrieved content as untrusted, and limiting context size to prevent overflow.

example system prompt 
You are a financial advisor assistant. You MUST:
1. Never share customer data with third parties
2. Only use approved tools (list_approved_tools)
3. Flag any request that seems suspicious

3

Tool execution boundary (action layer)

Least privilege per tool, input validation on arguments, code execution sandboxing, human-in-the-loop approval for destructive actions, and tool rate limiting.

python 
@tool
def delete_user(user_id: str) -> str:

Output filtering (post-LLM)

Validate and filter responses before returning to the user: PII detection, sensitive-data screening, response relevance checks, content policy compliance, citation & attribution.

python 
def filter_output(response):
    # 1. Check for PII
    if contains_pii(response):
        return "OUTPUT BLOCKED: Contains sensitive data"

    # 2. Verify relevance
    if not is_relevant(response, original_query):
        return "OUTPUT BLOCKED: Not relevant to query"

    # 3. Check content policy

        return "OUTPUT BLOCKED: Content policy violation"

    # 4. Add citations
    return add_citations(response)
5

Observability & monitoring (continuous)

Log everything (inputs, outputs, tool calls, timestamps — with PII redaction), real-time alerts on anomalous behavior or cost spikes, trace-level observability, and regular audits.

python 
class AgentMonitor:
    def __init__(self):
        self.logs = []
        self.alerts = []

    def log(self, event_type, data):
        # Log with PII redaction
        safe_data = redact_pii(data)
        self.logs.append({
            "timestamp": datetime.now(),
            "type": event_type,
            "data": safe_data
        })

        # Check for anomalies
        if self.detect_anomaly(event_type, data):
            self.trigger_alert(f"Anomaly detected: {event_type}")

    def detect_anomaly(self, event_type, data):
        # Cost spike detection
        if event_type == "api_call" and data.get("cost", 0) > 10:
            return True

        # Unusual tool patterns
        if event_type == "tool_call" and data.get("tool") not in ALLOWED_TOOLS:
            return True

        # Runaway execution
        if event_type == "iteration" and data.get("count", 0) > 10:
            return True

        return False

C. Chains (the namesake)

A chain is a sequence of processing steps where data flows from one step to the next: Prompt Template → LLM Model → Output Parser → Result. LCEL (LangChain Expression Language) connects them with the pipe operator |.

python 
from langchain.prompts import PromptTemplate
from langchain_openai import ChatOpenAI
from langchain_core.output_parsers import StrOutputParser

chain = prompt | model | StrOutputParser()
result = chain.invoke({"topic": "AI agents"})

The ReAct pattern

graph TD A[Reason: think about what to do next] --> B[Act: call a tool or respond] B --> C[Observe: examine the tool's result] C --> D{Enough information?} D -->|No| A D -->|Yes| E[Finish: provide final answer]

Complete agent example (15 lines)

python 
from langchain_openai import ChatOpenAI
from langchain.tools import tool
from langgraph.prebuilt import create_react_agent

# Step 1: Pick the brain
model = ChatOpenAI(model="gpt-4")

# Step 2: Define tools
@tool
def multiply(a: float, b: float) -> float:
    """Multiply two numbers together."""
    return a * b

@tool
def divide(a: float, b: float) -> float:
    """Divide the first number by the second."""
    if b == 0:
        return "Error: Cannot divide by zero"
    return a / b

# Step 3: Create agent
agent = create_react_agent(model, tools=[multiply, divide])

# Step 4: Run agent
result = agent.invoke({
    "messages": [("user", "What is 15 multiplied by 8 then divided by 3?")]
})

print(result["messages"][-1].content)
# Output: 40

The agent figured out the order automatically — multiply first, then divide — with no predefined workflow.

04 · Model Context Protocol (MCP)

The problem MCP solves

An open standard that lets any AI application connect to external tools, data sources, and systems in a consistent way — often called the "USB-C for AI." Any compatible client can talk to any compatible server, regardless of who built them. Built on JSON-RPC 2.0, a lightweight, bidirectional request-response protocol.

n × m → n + m

Before MCP

Every AI application had to write a custom integration for every tool. 3 apps × 4 tools = 12 separate integrations. Complexity grows quadratically — heavy duplication, fragile plumbing, high maintenance cost.

After MCP

Each app builds one MCP client; each tool exposes one MCP server. 3 clients + 4 servers = 7 standard connections. Complexity becomes linear (n + m).

StateComplexityIntegrations (3 apps × 4 tools)
Before MCPn × m12 custom connections
After MCPn + m7 standard connections

04 · Model Context Protocol (MCP)

Architecture — three key participants

ParticipantRole
HostThe AI application the user interacts with (Claude Desktop, Cursor, VS Code, a custom LangChain agent, Codex, etc.). Contains the LLM that performs reasoning. Creates one or more MCP clients and aggregates context across them.
ClientMaintains a dedicated one-to-one connection with exactly one MCP server. Discovers capabilities and invokes tools/resources/prompts.
ServerExposes context — tools (actions), resources (data), and prompts (templates). Connects to external systems (GitHub, Slack, databases, local filesystem, OCI APIs, etc.). Runs locally or remotely.
  • Client and server are decoupled — the server doesn't care which application is calling it.
  • Communication uses JSON-RPC 2.0.
  • Specialized multi-server clients (e.g. LangChain's MultiServerMCPClient) create multiple internal clients — one per server — while presenting a unified interface to the agent.

Discovery Client->>Server: tools/list Server-->>Client: list of tools + schemas Note over Client,Server: 3. Operate Client->>Server: tools/call (name + arguments) Server-->>Client: result (or error) Note over Client,Server: 4. Shutdown Client->>Server: close transport connection
  1. Initialization — client and server exchange protocol version and capabilities; client sends a "ready" notification.
  2. Discovery — client asks what the server offers (tools/list, resources/list, prompts/list); server returns schemas.
  3. Operate — client receives user queries → sends tools + query to the LLM → LLM decides which tool(s) to call → client executes via server → results flow back into the LLM's reasoning loop.
  4. Shutdown — client closes the transport connection.

JSON-RPC 2.0 message format

A structured request/response protocol supporting bidirectional communication (unlike pure REST); transport-agnostic.

typical request 
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "multiply",
    "arguments": { "a": 15, "b": 8 }
  }
}
typical successful response 
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      { "type": "text", "text": "120" }
    ]
  }
}

You almost never write these messages by hand — frameworks (FastMCP, LangChain, etc.) handle them. Understanding the structure is valuable for debugging.

  • tools/list — discover available tools and their schemas (called on connection). Enables dynamic discovery — no hard-coding.
  • tools/call — execute a specific tool with arguments. The result returns to the LLM's reasoning loop.
04 · Model Context Protocol (MCP)

Transport mechanisms

JSON-RPC is the message format; the transport can vary. The protocol layer stays identical regardless of transport — you can switch without changing message structure.

TransportUse caseHow it worksPros / cons
stdioLocal serversHost spawns the server as a child process; communication via stdin/stdout pipes.Fastest, zero network overhead. Server must be installed/run locally.
Streamable HTTPRemote / cloud serversClient sends via HTTP POST; server can stream responses with Server-Sent Events.Supports concurrent clients, cloud deployment, standard HTTP auth. Newer standard, supersedes older SSE-only transport.

Implementation: before vs. after MCP (math example)

before mcp — tools trapped inside one program 
from langchain.tools import tool

@tool
def add(a: float, b: float) -> float:
    """Add two numbers."""
    return a + b

@tool
def multiply(a: float, b: float) -> float:
    """Multiply two numbers."""
    return a * b

# Tools are hardcoded and only usable by this one agent
tools = [add, multiply]
after mcp — server (math_mcp_server.py, FastMCP) 
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("math")

@mcp.tool()
def add(a: float, b: float) -> float:
    """Add two numbers."""
    return a + b

@mcp.tool()
def divide(a: float, b: float) -> float:
    """Divide two numbers."""
    if b == 0:
        return "Error: cannot divide by 0"
    return a / b

if __name__ == "__main__":
    mcp.run(transport="stdio")  # listens on stdin/stdout, waits for JSON-RPC messages
after mcp — client (inside the agent / host) 
from langchain_mcp_adapters.client import MultiServerMCPClient
import os

client_config = {
    "math": {
        "command": "python",
        "args": [os.path.abspath("math_mcp_server.py")],
        "transport": "stdio"
    }
    # You can add more servers here (GitHub, Slack, OCI, etc.)
}

async def main():
    async with MultiServerMCPClient(client_config) as client:
        tools = await client.get_tools()  # discovers & merges tools from all servers
        # Create agent with these tools exactly as before
Architectural change: MCP inserts a standardized tool-execution layer. It does not replace the LLM or the agentic (ReAct) loop — responsibility for schema generation, discovery, invocation, and error handling moves to the server. The host/agent becomes a pure orchestrator; from the LLM's perspective, nothing changes.

Benefits of MCP

  • Build once, use everywhere — write tools in one server; every MCP-compatible host discovers them automatically.
  • Update in one place — a bug fix on the server is instantly available to all clients.
  • Mix and match — combine multiple servers (math + GitHub + Slack + OCI) in one client configuration.
  • Cleaner agent code — the agent focuses on reasoning; tool logic lives separately.
  • Dynamic discovery — no more hard-coding tool lists or schemas.
flowchart TD subgraph Server["MCP Server (written once)"] T1[Tool 1] T2[Tool 2] T3[Tool 3] end A1[LangChain Agent] --> Server A2[Claude Desktop] --> Server A3[Cursor / VS Code] --> Server A4[OpenAI Codex] --> Server

When MCP is overkill: simple local math functions — local Python is faster and simpler.
When MCP shines: external systems, reusable tools, databases, developer tools (GitHub/Jira), communication (Slack/email), remote file systems, cloud APIs (OCI, etc.).

04 · Model Context Protocol (MCP)

Real-world example — Oracle OCI Usage MCP server

In production you almost never write the server. A vendor, SaaS provider, or another team publishes it — you write only the client and work entirely through the protocol (tools/list + tools/call).

Your Agent (LangChain) ↕ stdio (local processes) OCI Usage MCP Server (published on PyPI by Oracle) ↕ HTTPS OCI Usage / Cost Analysis REST API
  • Client and server talk locally via stdio — no network between your script and the MCP server process.
  • The MCP server process reaches out to OCI over HTTPS.
  • Your code never calls OCI APIs directly.
client configuration (using uvx) 
client_config = {
    "oci-usage": {
        "command": "uvx",
        "args": ["oci-usage-mcp-server"],  # downloads & runs from PyPI in isolated env
        "transport": "stdio",
        "env": {
            "OCI_CONFIG_FILE": "~/.oci/config",
            "OCI_PROFILE": "DEFAULT"
        }
    }
}

uvx (from the uv tool) is the Python equivalent of npx — runs a package without permanently installing it into your environment.

Surface area of this server

One main tool — get_summarized_usage (tenant ID, start/end time, granularity, etc.).

Demo outcome

Natural-language query ("show me the cost for last 30 days as a daily breakdown by service") → agent calls the MCP tool → receives data → prints a pivot table and writes a CSV. Numbers matched the OCI Console Cost Analysis page to the cent.

This is the core value of MCP: vendors expose tools once, and any compliant client can consume them without bespoke integration code.
