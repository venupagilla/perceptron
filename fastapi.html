01 · Introduction

What is an API?

The core concept everything else builds on — a clear definition first.

API stands for Application Programming Interface. In simple terms, an API is a set of rules and protocols that allows one piece of software to communicate with another piece of software.

A contract between two pieces of software

An API acts as a contract that defines:

  • What kind of requests can be made
  • In what format the data should be sent
  • What kind of response will be returned
  • How errors or authentication should be handled

You don't need to know the internal workings of the other software — you just follow the rules of the API.

01 · Introduction

Why FastAPI is chosen

The reasons it stands out

FastAPI is one of the most popular modern Python frameworks for building APIs. It is fast (one of the highest-performing Python web frameworks), easy to learn, automatically generates beautiful interactive documentation (Swagger UI), and has excellent support for asynchronous operations — which is very useful when serving ML inference requests at scale.

01 · Introduction

The restaurant analogy

One of the clearest and most commonly used analogies for explaining APIs.

RestaurantAPI
You (the customer)The Client (frontend app, mobile app, or another service)
The MenuThe API documentation (tells you what you can order and how)
The WaiterThe API itself (takes your order, communicates with the kitchen, brings the food back)
The Kitchen (chefs & equipment)The Server / Backend (where the work happens — database queries, running your ML model, calculations)
The Food you receiveThe Response (JSON data, prediction result, list of items)

How the flow works

  1. You sit down and look at the menu → decide what to order.
  2. You tell the waiter your order (request).
  3. The waiter goes to the kitchen and tells the chefs (the API forwards the request to the server logic).
  4. Chefs prepare the food (server processes the request — e.g., runs your ML model on input data).
  5. Waiter brings the prepared dish back to your table (server sends the response back through the API).

Important lessons from this analogy

  • As a customer, you never enter the kitchen or tell the chefs how to cook — you only interact via the waiter and menu.
  • The kitchen can completely change its recipes, tools, or even chefs — as long as the menu (API contract) stays the same, you won't notice any difference.
  • The waiter hides all the complexity of the kitchen from you.
  • If the restaurant adds new dishes to the menu, you can order them without knowing how they are prepared.
Another quick analogy: a wall socket is an API for electricity. You just plug in your device using the correct plug shape — you don't need to understand how the power plant generates electricity.

01 · Introduction

Why APIs are important for machine learning

The core focus of these notes: turning trained models into usable products.

The common pain point

You train a great ML model in a Jupyter notebook. It works perfectly on your laptop. But how do you let real users or other applications use it?

Solution: wrap your model inside an API.

Typical ML API workflow

  1. Train and save your model (using pickle, joblib, ONNX, etc.).
  2. Load the model inside a FastAPI server.
  3. Create an endpoint (e.g., /predict) that accepts input features.
  4. The endpoint runs inference on the model and returns the prediction.

Benefits of exposing ML models via APIs

  • Your model stays secure on the server — no one downloads your weights.
  • Anyone (frontend team, mobile developers, other services) can use it without knowing ML.
  • Easy to scale — handle thousands of prediction requests per second.
  • You can update or A/B test models by changing the backend without touching the clients.
  • Supports real-time applications (chatbots, recommendation systems, image classifiers, etc.).

Examples of ML APIs you might build

Image classification

Upload a photo → get "cat" with 98% confidence.

Sentiment analysis

Send customer review text → get positive/negative score.

House price prediction

Send features (area, rooms, location) → get predicted price.

Recommendation engine

Send user ID → get list of suggested products.

Custom LLM endpoint

Send prompt → get generated text (your own fine-tuned model).

Illustrative FastAPI + ML code snippet

python 
from fastapi import FastAPI
from pydantic import BaseModel
import joblib

app = FastAPI(title="My ML Prediction API")

# Load trained model when the server starts
model = joblib.load("my_trained_model.pkl")

# Define the expected input data structure with validation
class InputData(BaseModel):
    feature1: float
    feature2: float
    feature3: int
    # ... add all your model features

@app.post("/predict")
def predict(data: InputData):
    # Convert input to the format your model expects
    features = [[data.feature1, data.feature2, data.feature3]]

    # Run inference
    prediction = model.predict(features)[0]

    return {"prediction": prediction, "model_version": "1.0"}

How a client would call this

bash · curl 
curl -X POST "http://localhost:8000/predict" \
  -H "Content-Type: application/json" \
  -d '{"feature1": 5.1, "feature2": 3.5, "feature3": 1}'

This returns a clean JSON response with the prediction.

Advantages of using FastAPI for ML

  • Automatic data validation (Pydantic) prevents bad inputs from crashing your model.
  • Built-in interactive docs so frontend teams can test endpoints easily.
  • Async support for handling many simultaneous requests.
  • Very high performance.
Final key takeaway: an API is simply a standardized bridge that lets different software components talk to each other reliably. In the context of machine learning, APIs are the practical way to turn your trained models from isolated notebook experiments into real, usable products that power apps and services.

02 · HTTP Methods

What are HTTP methods?

Standardized actions that tell the server what to do with a resource.

Definition

HTTP Methods (also called HTTP Verbs) are standardized actions that tell the server what to do with a resource. They are part of the HTTP protocol — the foundation of how web browsers, mobile apps, and other clients communicate with servers.

Key characteristics

  • Methods are written in UPPERCASE (GET, POST, etc.).
  • They define the intent of the request.
  • Each method has different behaviors regarding safety (does it change data?), idempotency (does repeating the request give the same result?), and what data it can carry.

The 4 most commonly used HTTP methods

These cover ~95% of what you'll use in real FastAPI projects, especially for ML APIs.

GET

Retrieve / Read data

POST

Create / Send new data

PUT

Update / Replace entire resource

DELETE

Remove / Delete a resource

There is also PATCH for partial updates, mentioned in many FastAPI tutorials — the focus here is mainly on the four core ones.
02 · HTTP Methods

GET method

Definition

GET is used to request data from the server. It asks the server to send back information without modifying anything.

Key properties

  • Safe — does not change server state.
  • Idempotent — repeating the same GET request multiple times gives the same result (no side effects).
  • No request body — you usually pass data via URL parameters or path.

Real-world examples

  • Opening a webpage (your browser sends GET to fetch HTML).
  • Fetching weather data.
  • In ML: getting the current model version, listing all past predictions, or retrieving model metadata.
python 
from fastapi import FastAPI

app = FastAPI()

items = ["Apple", "Banana", "Cherry"]  # Simulated database

@app.get("/items")  # GET method
def get_all_items():
    return {"items": items}

@app.get("/items/{item_id}")  # Path parameter
def get_single_item(item_id: int):
    return {"item": items[item_id]}
Analogy: asking a librarian for a specific book — you only read, you don't change the library.
02 · HTTP Methods

POST method

Definition

POST is used to send data to the server to create a new resource.

  • Not safe — it changes server state.
  • Not idempotent — repeating it may create multiple resources.

Real-world examples

  • Submitting a form (sign-up, contact form).
  • Uploading a file.
  • In ML: sending input features (sepal length, etc.) to get a prediction from a model.
python 
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):  # Request body validation
    name: str
    description: str | None = None

items = []

@app.post("/items")  # POST method
def create_item(item: Item):
    items.append(item)
    return {"message": "Item created", "item": item}
Analogy: placing an order at a restaurant — you are creating a new order in the system.
02 · HTTP Methods

PUT method

Definition

PUT is used to update an existing resource or replace it entirely. If the resource doesn't exist, some implementations create it (though in practice, we often check first).

  • Idempotent — repeating the same PUT request multiple times leaves the server in the same state.
  • Usually includes the full updated resource in the request body.

Real-world examples

  • Updating user profile information.
  • In ML: updating a model's configuration, replacing an old model version with a new trained one.
python 
@app.put("/items/{item_id}")
def update_item(item_id: int, item: Item):
    # In real code: check if exists, then replace
    if 0 <= item_id < len(items):
        items[item_id] = item
        return {"message": "Item updated", "item": item}
    return {"error": "Item not found"}
Analogy: replacing an old book in the library with a new edition — the entire resource is updated/replaced.
02 · HTTP Methods

DELETE method

Definition

DELETE is used to remove a resource from the server.

  • Not safe.
  • Idempotent — deleting the same resource twice should not cause errors (second time it may just say "already deleted").

Real-world examples

  • Deleting a social media post.
  • In ML: removing old prediction logs to save storage, or deleting a deprecated model version.
python 
@app.delete("/items/{item_id}")
def delete_item(item_id: int):
    if 0 <= item_id < len(items):
        deleted = items.pop(item_id)
        return {"message": "Item deleted", "deleted_item": deleted}
    return {"error": "Item not found"}
Analogy: throwing away a book you no longer want from the library shelf.

02 · HTTP Methods

Key takeaways & best practices

  • Always choose the correct HTTP method based on the action — it makes your API intuitive and follows REST principles.
  • GET should never change data (important for caching, security, and browser behavior).
  • Use Pydantic models (BaseModel) with POST and PUT for automatic validation of incoming data — crucial when accepting features for ML predictions.
  • In production ML APIs, combine these with proper error handling and status codes (e.g., 200 OK, 201 Created, 404 Not Found, 204 No Content for DELETE).
  • The automatic Swagger UI in FastAPI makes testing these methods extremely easy.

03 · Path & Query Parameters

Path parameters

Dynamic parts of the URL that let you target a specific resource.

Definition

Path parameters are dynamic parts of the URL path that allow you to capture variable values directly from the URL. They are required and used to identify or target a specific resource. They appear inside curly braces {} in the route definition.

Real-world examples

  • /users/{user_id} → fetches details of one user.
  • /products/{product_id} → gets one product.
  • In ML: /predict/{model_id} or /results/{prediction_id}.
Analogy: think of a library catalog. The shelf number in the URL (like /books/{shelf_number}) points to a specific book. Without it, you only get the entire catalog.

Key characteristics

  • Part of the URL path (e.g., http://localhost:8000/patient/P01).
  • FastAPI automatically extracts the value and passes it to your function.
  • Can have type hints (str, int, float, etc.) for validation.
  • Required by default — if missing, the endpoint won't match.

FastAPI implementation

python 
from fastapi import FastAPI, HTTPException
import json

app = FastAPI()

# Load patient data (simulated database)
with open("patients.json") as f:
    patients = json.load(f)

@app.get("/patient/{patient_id}")   # Path parameter
def get_patient(patient_id: str):
    for patient in patients:
        if patient["id"] == patient_id:
            return patient
    # If not found → proper error
    raise HTTPException(status_code=404, detail="Patient not found")

How it works

  • URL: http://127.0.0.1:8000/patient/P01
  • patient_id receives "P01".
  • Search the list and return matching data or raise 404.

Improving with the Path function

python 
from fastapi import Path

@app.get("/patient/{patient_id}")
def get_patient(patient_id: str = Path(
    description="ID of the patient in the database",
    example="P01",
    min_length=2,
    max_length=10
)):
    # ... same logic

This adds rich metadata that appears beautifully in the automatic Swagger UI documentation.

03 · Path & Query Parameters

Query parameters

Optional key-value pairs for filtering, sorting, searching, or pagination.

Definition

Query parameters are optional key-value pairs added to the end of a URL after a ? symbol. They are used for filtering, sorting, searching, or pagination without changing the main URL path. They do not affect route matching — they are passed as function arguments.

Syntax: http://localhost:8000/sort?sort_by=weight&order=descending

Real-world examples

  • Google search: https://google.com/search?q=fastapi
  • Video platforms: ?v=video_id&list=playlist
  • In ML: /predictions?min_confidence=0.85&sort_by=score&limit=10

Key characteristics

  • Optional (can have defaults).
  • Can be multiple in one request.
  • Great for flexibility without creating new endpoints.

FastAPI implementation (sorting example)

python 
from fastapi import Query, HTTPException

@app.get("/sort")
def sort_patients(
    sort_by: str = Query(
        description="Field to sort by",
        example="weight",
        enum=["weight", "height", "bmi"]   # Restricts values
    ),
    order: str = Query(
        default="ascending",
        description="Sort order",
        enum=["ascending", "descending"]
    )
):
    if sort_by not in ["weight", "height", "bmi"]:
        raise HTTPException(status_code=400, detail="Invalid sort_by value")

    # Sorting logic
    reverse = (order == "descending")
    sorted_patients = sorted(
        patients,
        key=lambda p: p[sort_by],
        reverse=reverse
    )

    return {"sorted_by": sort_by, "order": order, "patients": sorted_patients}

How query parameters shine

  • Clients can call /sort?sort_by=weight (uses default order).
  • Or /sort?sort_by=bmi&order=descending.
  • FastAPI validates automatically and shows everything in Swagger UI.
Analogy: query parameters are like extra instructions on your restaurant order — "Make it spicy? Extra cheese? No onions?" They modify the main request without changing what you are ordering.

03 · Path & Query Parameters

Final key takeaways

  • Path Parameters make your API URLs dynamic and resource-specific — use them when you need to target one item.
  • Query Parameters add optional power for filtering and customization — use them when you want flexibility on the same endpoint.
  • Always use Path() and Query() for better validation, defaults, descriptions, and automatic docs.
  • Combine with proper HTTP status codes and HTTPException to make your API professional and client-friendly.
  • These two tools turn a static API into a flexible, production-ready service — a perfect foundation for ML model serving endpoints.

For ML context: path params fetch a saved prediction by its unique ID; query params filter predictions by date range, confidence threshold, or model version; sort by probability score.

04 · POST Request

What is a request body?

Definition

Request Body is the payload/data sent in the body of an HTTP request (mainly used with POST, PUT, PATCH). It is ideal for sending complex, structured, or large data (e.g., a full patient object with multiple fields). Unlike query parameters (visible in URL, limited length) or path parameters (for identifiers), the request body is designed for object creation/updates. The common format is JSON.

Why request body in FastAPI?

  • FastAPI automatically parses the JSON.
  • Validates it against a Pydantic model.
  • Provides clear, field-level error messages (422 Unprocessable Entity) if validation fails.
  • Generates interactive documentation (Swagger UI at /docs) showing the exact request schema.
  • Reduces boilerplate — no manual parsing or type checking needed.

Comparison

MethodBody usage
GETUsually no body (uses query/path params)
POSTUses body to send the resource to create
04 · POST Request

Step 1: define the Pydantic model (Patient)

The model handles data validation, field constraints, and computed/derived fields (BMI and verdict).

python 
from pydantic import BaseModel, Field, computed_field
from typing import Literal, Annotated
from fastapi import FastAPI, HTTPException
from fastapi.responses import JSONResponse
import json
import os

app = FastAPI()

class Patient(BaseModel):
    id: Annotated[str, Field(..., description="Unique patient ID", examples=["P001"])]
    name: Annotated[str, Field(..., min_length=2, description="Full name of the patient")]
    city: str
    age: Annotated[int, Field(..., gt=0, le=120, description="Age in years")]
    gender: Annotated[Literal["male", "female", "other"], Field(description="Gender")]
    height: Annotated[float, Field(..., gt=0, description="Height in meters")]
    weight: Annotated[float, Field(..., gt=0, description="Weight in kg")]

    @computed_field
    @property
    def bmi(self) -> float:
        """Calculate Body Mass Index (BMI)"""
        return round(self.weight / (self.height ** 2), 2)

    @computed_field
    @property
    def verdict(self) -> str:
        """Health verdict based on BMI"""
        if self.bmi < 18.5:
            return "Underweight"
        elif self.bmi < 25:
            return "Normal"
        elif self.bmi < 30:
            return "Overweight"
        else:
            return "Obese"

Key features explained

FeatureWhat it does
Annotated + Field()Adds validation rules (gt, le, min_length), descriptions, and examples for documentation.
LiteralRestricts gender to only allowed values.
@computed_fieldAutomatically calculates bmi and verdict when the model is created. These fields are not sent by the client but appear in responses and saved data.

04 · POST Request

Step 3: the POST endpoint

python 
@app.post("/create")
def create_patient(patient: Patient):   # Request Body declared here
    data = load_data()

    # Business rule: Check for duplicate ID
    if patient.id in data:
        raise HTTPException(
            status_code=400,
            detail="Patient with this ID already exists"
        )

    # Save the full patient data (including computed fields)
    data[patient.id] = patient.model_dump()

    save_data(data)

    return JSONResponse(
        status_code=201,
        content={
            "message": "Patient created successfully",
            "patient_id": patient.id
        }
    )

  • Idempotent — repeating the exact same request multiple times produces the same result as doing it once (no additional side effects). PUT and DELETE are idempotent; POST is not.
  • Safe — does not change server state (only GET is safe).

Analogies

PUT

Replacing an old book in a library shelf with a new, updated edition. If you send the same replacement twice, the shelf still has the same final book.

DELETE

Throwing a file into the trash. Sending the delete command again doesn't change the fact that the file is already gone.

Pydantic models (foundation for all endpoints)

The Patient model (re-used) plus a new PatientUpdate model for safe partial updates.

Patient model (full validation + computed fields)

python 
from pydantic import BaseModel, Field, computed_field
from typing import Annotated, Literal

class Patient(BaseModel):
    id: Annotated[str, Field(..., description='ID of the patient', examples=['P001'])]
    name: Annotated[str, Field(..., description='Name of the patient')]
    city: Annotated[str, Field(..., description='City where the patient is living')]
    age: Annotated[int, Field(..., gt=0, lt=120, description='Age of the patient')]
    gender: Annotated[Literal['male', 'female', 'others'], Field(..., description='Gender of the patient')]
    height: Annotated[float, Field(..., gt=0, description='Height of the patient in mtrs')]
    weight: Annotated[float, Field(..., gt=0, description='Weight of the patient in kgs')]

    @computed_field
    @property
    def bmi(self) -> float:
        bmi = round(self.weight / (self.height ** 2), 2)
        return bmi

    @computed_field
    @property
    def verdict(self) -> str:
        if self.bmi < 18.5:
            return 'Underweight'
        elif self.bmi < 25:
            return 'Normal'
        elif self.bmi < 30:
            return 'Overweight'
        else:
            return 'Obese'

Key concepts explained

  • BaseModel + Annotated[Type, Field(...)] → automatic validation, Swagger documentation, and examples.
  • gt=0, lt=120 → built-in validation rules (raises 422 error on invalid data).
  • @computed_field (Pydantic v2) → fields that are calculated automatically on every output. You never send bmi or verdict in the request body — they are derived from height + weight.
Analogy: think of a smart Excel sheet. You enter raw numbers (height, weight); the sheet automatically calculates BMI and health verdict. Pydantic does the same at the API level.

PatientUpdate model (partial updates only)

python 
class PatientUpdate(BaseModel):
    name: Annotated[Optional[str], Field(default=None)]
    city: Annotated[Optional[str], Field(default=None)]
    age: Annotated[Optional[int], Field(default=None, gt=0)]
    gender: Annotated[Optional[Literal['male', 'female']], Field(default=None)]
    height: Annotated[Optional[float], Field(default=None, gt=0)]
    weight: Annotated[Optional[float], Field(default=None, gt=0)]

Why a separate model?

All fields are optional (default=None). This allows partial updates (e.g., change only age and weight). The magic happens with .model_dump(exclude_unset=True) later.

Helper functions (load_data & save_data)

Used in every endpoint for persistence: load_data() reads patients.json into a Python dict (key = patient_id); save_data(data) writes the dict back to JSON. These are simple file I/O helpers — in production you would replace them with a real database.

05 · PUT & DELETE

PUT endpoint — update patient

Route: PUT /edit/{patient_id}

python 
from fastapi import HTTPException
from fastapi.responses import JSONResponse

@app.put('/edit/{patient_id}')
def update_patient(patient_id: str, patient_update: PatientUpdate):
    data = load_data()

    if patient_id not in data:
        raise HTTPException(status_code=404, detail='Patient not found')

    existing_patient_info = data[patient_id]
    # Only the fields actually sent by the user
    updated_patient_info = patient_update.model_dump(exclude_unset=True)

    # Merge changes
    for key, value in updated_patient_info.items():
        existing_patient_info[key] = value

    # Re-add ID and trigger Pydantic recomputation of bmi/verdict
    existing_patient_info['id'] = patient_id
    patient_pydandic_obj = Patient(**existing_patient_info)
    existing_patient_info = patient_pydandic_obj.model_dump(exclude='id')

    data[patient_id] = existing_patient_info
    save_data(data)

    return JSONResponse(status_code=200, content={'message': 'patient updated'})

Step-by-step walkthrough

  1. Load current data.
  2. Check if patient exists → else 404.
  3. patient_update.model_dump(exclude_unset=True) → only changed fields become a dictionary (the key trick for partial updates).
  4. Loop and overwrite only those fields in the existing record.
  5. Force id back in and instantiate a full Patient object → Pydantic automatically recomputes bmi and verdict.
  6. Convert back to dict (exclude id because it's the dictionary key).
  7. Save and return success.

Example request

Method: PUT
URL: http://127.0.0.1:8000/edit/P001
Body (JSON — only send what you want to change):

{
  "age": 35,
  "weight": 75.5
}

Response: {"message": "patient updated"} (200 OK)

The patient's BMI and verdict are automatically updated in the stored record.

Analogy: you're filling out only the changed boxes on a medical form. The system recalculates everything else automatically and saves the new version over the old one.

06 · Pydantic

Why is Pydantic used?

One of the most important libraries in modern Python — especially for building APIs (FastAPI), data pipelines, and robust applications.

The real problem it solves

Python is dynamically typed. Type hints (age: int) are not enforced at runtime — they only help IDEs, static type checkers (mypy), and developers.

Problems without proper validation

  • User sends "30" (string) instead of 30 → later code crashes or behaves unexpectedly.
  • Invalid data sneaks in: negative age, malformed email, missing fields, extra unwanted fields.
  • You write repetitive, ugly validation code everywhere.
  • Inconsistent error messages across the application.
  • Security risks in APIs, config files, or data ingestion.
  • High maintenance cost — every schema change requires updating validation logic in multiple places.
python · the manual approach 
if not isinstance(age, int) or age <= 0 or age > 120:
    raise ValueError("Invalid age")

Real-world use cases

FastAPI

Automatic request validation + clear error responses.

Data ingestion

CSV, JSON, external APIs.

Configuration management

Environment variables, YAML, JSON.

Microservices

Enforcing contracts between services.

Machine Learning

Validating input features before model prediction.

Form handling

Web applications.

What Pydantic gives you

  • Declarative validation using Python type hints.
  • Automatic type coercion (where safe): "28" → 28, "true" → True.
  • Rich, structured ValidationError with exact field location and message.
  • Excellent error messages perfect for APIs.
  • High performance — Pydantic V2 core is rewritten in Rust.
  • DRY principle: define the schema once, use everywhere.
Bottom line: Pydantic turns "hope the data is correct" into "guaranteed the data is correct and clean."
06 · Pydantic

How does Pydantic work?

A clean three-step process.

  1. Define a model by inheriting from BaseModel.
  2. Validate & Parse raw data (dict, JSON, etc.).
  3. Use the resulting clean Python object.

Basic model definition

python 
from pydantic import BaseModel, Field
from typing import Optional, List
from datetime import datetime

class User(BaseModel):
    id: int                    # required
    name: str                  # required
    email: Optional[str] = None   # optional (Python 3.9+ style)
    age: int = 18              # default value
    is_active: bool = True
    tags: List[str] = Field(default_factory=list)   # mutable default (correct way)
    created_at: datetime = Field(default_factory=datetime.now)

Creating a model instance (validation)

python 
raw_data = {
    "id": 101,
    "name": "Venu",
    "email": "venu@example.com",
    "age": "28",           # string → automatically coerced to int
    "tags": ["python", "fastapi"]
}

user = User.model_validate(raw_data)        # Recommended in V2
# user = User(**raw_data)                   # Still works

print(user.age)           # 28 (int)
print(user.created_at)    # datetime object

What happens internally?

  1. Pydantic inspects type annotations.
  2. For every field: checks presence (if required), performs type coercion if possible, runs built-in validators (EmailStr, conint(gt=0), etc.), runs your custom validators.
  3. If all pass → creates model instance with correct Python types.
  4. If any fails → raises ValidationError with a detailed error list.

Key instantiation methods (V2)

MethodPurpose
Model.model_validate(data)From dict or object
Model.model_validate_json(json_str)From JSON string
Model(**data)Legacy but still supported

Strict mode (powerful V2 feature)

By default, Pydantic is lenient (coerces types). You can make it strict:

python 
from pydantic import ConfigDict

class User(BaseModel):
    model_config = ConfigDict(strict=True)   # No coercion allowed

    age: int

Common pitfalls

  • Using [] or {} as default (mutable) → use Field(default_factory=list).
  • Extra fields: default behavior is extra='ignore'. Use extra='forbid' to reject unknown fields.
06 · Pydantic

Field validator (@field_validator)

Used for custom validation or transformation of a single field.

Basic syntax

python 
from pydantic import field_validator, FieldValidationInfo
from typing import Any

class User(BaseModel):
    name: str
    age: int

    @field_validator('name')
    @classmethod
    def validate_name(cls, v: str) -> str:
        v = v.strip()
        if len(v) < 2:
            raise ValueError('Name must be at least 2 characters long')
        return v.title()          # Convert to Title Case

Validator modes (important V2 concept)

ModeWhen it runsBest Use Case
'before'Before type coercionCleaning raw input (strip, split)
'after'After type coercion (default)Business rules on correct type
'plain'Skips Pydantic's internal validationRare, full control

Accessing other fields

python 
@field_validator('age')
@classmethod
def check_adult(cls, v: int, info: FieldValidationInfo) -> int:
    if v < 18:
        raise ValueError('User must be at least 18 years old')

    # Access other fields (only available in 'after' mode)
    if info.data.get('name', '').lower() == 'admin' and v < 30:
        raise ValueError('Admin must be at least 30 years old')

    return v

Applying to multiple fields

python 
@field_validator('name', 'email', mode='before')
@classmethod
def strip_strings(cls, v: Any) -> Any:
    if isinstance(v, str):
        return v.strip()
    return v

Best practices

  • Keep each validator focused on one job.
  • Always raise ValueError or PydanticCustomError.
  • Use mode='before' for sanitization, mode='after' for rules.
06 · Pydantic

Model validator (@model_validator)

Used when validation logic involves multiple fields (cross-field validation).

Modes

  • 'before' → runs on raw input dict (before field validation).
  • 'after' → runs after all fields are validated (most common).

Example: password confirmation

python 
from pydantic import model_validator

class UserRegistration(BaseModel):
    username: str
    password: str
    password_confirm: str

    @model_validator(mode='after')
    def check_passwords_match(self):
        if self.password != self.password_confirm:
            raise ValueError('Passwords do not match')
        return self          # Must return self

Example: conditional requirement

python 
class Patient(BaseModel):
    age: int
    emergency_contact: Optional[str] = None

    @model_validator(mode='after')
    def require_emergency_for_seniors(self):
        if self.age >= 65 and not self.emergency_contact:
            raise ValueError('Senior patients (65+) must provide an emergency contact')
        return self

Best use cases

Password matching

Confirm two fields agree.

Date validation

e.g., start_date < end_date.

Business rules

Spanning multiple fields.

Conditional logic

Complex cross-field conditions.

06 · Pydantic

Computed fields (@computed_field)

Fields that are automatically calculated from other fields. They are not accepted as input.

python 
from pydantic import computed_field

class Rectangle(BaseModel):
    width: float
    height: float

    @computed_field
    @property
    def area(self) -> float:
        return self.width * self.height

    @computed_field
    @property
    def perimeter(self) -> float:
        return 2 * (self.width + self.height)
python · usage 
rect = Rectangle(width=10, height=5)
print(rect.area)                    # 50.0
print(rect.model_dump())            # includes area and perimeter

Why @computed_field + @property?

  • Makes the computed value appear in .model_dump(), JSON schema, etc.
  • Shows as readOnly in generated OpenAPI docs.

Common uses

  • Full name from first_name + last_name.
  • BMI from weight & height.
  • Age from date_of_birth.
  • Any derived business metric.

Very useful pattern

u = User(name="Venu")   # age and is_active use defaults

Final best practices & tips

  • Always prefer V2 syntax (model_validate, model_dump, field_validator, etc.).
  • Use Field(...) for rich metadata: gt, le, pattern, alias, description, etc.
  • Prefer model_validate() over User(**data).
  • Order of validators: fields defined order + decorator order.
  • For configuration, use pydantic_settings.BaseSettings.
  • Always handle ValidationError gracefully in APIs.
  • Test edge cases: missing fields, wrong types, None, extra fields, deep nesting.
