01 · DevOps & SDLC

DevOps fundamentals

DevOps is a culture and a software delivery model — a union of people, process, and tools for continuous delivery of value.

Definition & origins

  • Introduced in 2006, standardized in 2013.
  • Definition: a union of people, processes, and tools that enables continuous delivery of value to end users.
  • Core concepts: People (culture & collaboration), Process (automation & efficiency), Tools (technology & integration).

Fundamentals of DevOps

  • Culture & SDLC model — a cultural shift in software development and operations; a modern approach to the software development life cycle.
  • Software delivery approach — a new methodology for faster, more reliable project delivery.
  • Automation — leveraging tools to automate manual tasks (CI/CD, Infrastructure as Code, monitoring).
  • Speed & stability — enables rapid changes while maintaining system stability.
  • Measured by success metrics:

Speed of delivery

Deployment frequency and lead time for changes — how often and how quickly value ships.

Stability of service

Mean time to recovery (MTTR) and change failure rate — how well the system holds up.

Bottom line: Waterfall's main goal is quality; Agile's main goal is quality + performance; DevOps's main goal is agile + automation.
01 · DevOps & SDLC

The DevOps lifecycle

A continuous loop from planning through monitoring — feedback from the last phase feeds the next cycle.

graph LR A[Plan] --> B[Code] B --> C[Build] C --> D[Test] D --> E[Release & Deploy] E --> F[Operate] F --> G[Monitor] G -->|feedback| A

1 · Plan

Teams define business requirements, project scope, and features for the next cycle — creating a roadmap, prioritizing tasks, and managing backlogs.

2 · Code

Developers write the code for planned features. Relies heavily on version control systems like Git to manage changes and enable collaboration.

3 · Build

Code is compiled and packaged. This is the core of Continuous Integration (CI) — automated tools (like Jenkins or GitLab CI) pull the code and create a build, often a container image or executable.

4 · Test

Built software undergoes continuous testing — automated unit, integration, and security tests validate the code before it reaches users.

5 · Release & Deploy

After tests pass, the build is released to production via Continuous Delivery/Deployment (CD) — faster, more reliable releases.

6 · Operate

The operations team manages the running application — configuring servers, managing infrastructure, scaling resources, and keeping it available.

7 · Monitor: performance and stability are tracked in production — usage, errors, and system health data is collected, analyzed, and channeled back into the Plan phase, restarting the cycle for continuous improvement.
01 · DevOps & SDLC

SDLC evolution timeline

How software development processes matured from an unrecognized field into disciplined engineering.

1962

The U.S. recognizes IT as a separate industry

Marked the formal beginning of IT as a field apart from general electronics or telecommunications. Before this, access to computers was largely restricted to government entities.

1968

Early discussions on software development methodologies

The question was raised: "What steps should be taken to formalize and improve the process of software development?" — early debates about managing software complexity, quality, and delivery that laid the groundwork for structured software engineering practices.

Pre-SDLC era

Influence of Lean manufacturing

Before the SDLC, a process known as Lean was already in use — but only in manufacturing. It was not directly applicable to software because of the intangible, creative, and iterative nature of software, which highlighted the need for a tailored approach.

1970s

Rise of structured programming and SDLC models

Introduction of structured programming and formal SDLC models, most notably the Waterfall model — bringing discipline, predictability, and clarity, with phases like requirements analysis, design, implementation, testing, and maintenance.

1984

India recognizes IT as a separate industry

More than two decades after the U.S., helping catalyze India's software and services sector and its emergence as a global IT hub.

1990s → 2001

Agile Manifesto and DevOps beginnings

In response to Waterfall's limitations, the Agile Manifesto was introduced in 2001 (with roots in the 1990s) — promoting iterative development, customer collaboration, and flexibility. Early DevOps concepts emerged, emphasizing collaboration between development and operations teams to improve deployment frequency and software quality.

2000s

Cloud computing and globalization

The rise of cloud computing, SaaS, and platform-based infrastructures; accelerated global outsourcing of IT services; maturation of open-source software, mobile technologies, and the foundational growth of AI and big data analytics.

01 · DevOps & SDLC

What is SDLC?

SDLC (Software Development Life Cycle) is a structured engineering practice followed by developers and operations teams to produce software — ensuring delivery of high-quality software that is completed on time, within budget, and meets user requirements.

SDLC was formally defined in 1968 at the NATO Software Engineering Conference, marking the beginning of software engineering as a disciplined field.

Key phases

graph LR A[Planning & Requirements] --> B[Design] B --> C[Implementation / Coding] C --> D[Testing] D --> E[Deployment] E --> F[Maintenance]
  1. Planning & Requirements — define objectives and gather requirements.
  2. Design — create system architecture and detailed specifications.
  3. Implementation (Coding) — write the software based on the design.
  4. Testing — ensure the software works as intended through QA.
  5. Deployment — release the software to users.
  6. Maintenance — update and improve the software post-release.

Why SDLC matters

Provides a clear roadmap for development. Enhances quality, reduces risks, and improves team collaboration. Forms the foundation for modern methodologies like Agile and DevOps.

Team structure

Developer team

Includes professionals involved in planning, designing, coding, and testing.

Operations team

Handles all activities after testing — deployment, monitoring, and maintenance.

01 · DevOps & SDLC

The Waterfall model

The first formal process model for software development — a strict sequential flow.

Introduced in 1972 by Winston W. Royce, who initially described it as a flawed model that needed iteration, though it was later adopted as a linear approach.

Phases of the Waterfall model

PhaseActivityParticipants
1 · Planning & RequirementsGather detailed requirements from stakeholders.Project managers, business analysts, senior engineers
2 · DesignCreate the software blueprint — system and architectural design.System architects and designers
3 · Implementation (Coding)Developers write code based on the design specifications.Programmers and developers
4 · TestingFunctionality checking and bug identification.QA engineers and testers
5 · MaintenanceDeliver the software and provide post-release support.Operations and maintenance teams

Features

  • Simple and easy to implement — due to its linear and structured nature.
  • Low cost — minimal overhead in terms of process management.
  • Low usage — only ~4% of software projects globally use the pure Waterfall model today.
  • Best suited for small projects with well-understood and stable requirements.

Concerns and limitations

  • Not suitable for large projects — rigidity makes large, complex, or evolving projects hard to manage.
  • Outdated ideology by 1985 — lack of flexibility and iteration led to its decline in favor of iterative and agile approaches.
  • No room for changes — once a phase is completed, revisiting it is difficult or costly.
  • Late testing phase — defects are only discovered late in the cycle, increasing the cost and effort of fixes.
Average time to complete projects: Waterfall — 3 to 5 years · Agile — 1 year · DevOps — 3 to 6 months.

Agile values & principles

The Agile foundation recommends agile values and agile principles (Manifesto 2001).

The four core values

1 · Individuals and interactions

Over processes and tools. People and how they work together matter more than rigidly following tools or processes.

2 · Working software

Over comprehensive documentation. Delivering something functional and valuable beats producing paperwork that does not directly help the customer.

3 · Customer collaboration

Over contract negotiation. An ongoing partnership with the customer is more valuable than just sticking to a contract.

4 · Responding to change

Over following a plan. Adapting to change is better than rigidly following a predefined plan.

The 12 Agile principles

  • Customer satisfaction through early and continuous delivery of useful software.
  • Welcome changing requirements, even late in development — change is an advantage, not a disruption.
  • Deliver working software frequently — short cycles (weeks, not months) to show progress.
  • Business people and developers work together daily — collaboration between tech and business is essential.
  • Build projects around motivated individuals — trust people, support them, and let them self-organize.
  • Face-to-face conversation is the best way to communicate — direct, clear communication beats endless documents.
  • Working software is the primary measure of progress — functionality delivered matters more than reports or plans.
  • Sustainable development pace — teams should maintain a steady, long-term rhythm without burnout.
  • Continuous attention to technical excellence and good design — high-quality code and design make agility possible.
  • Simplicity — the art of maximizing the amount of work not done — is essential; do only what adds real value.
  • Best architectures, requirements, and designs emerge from self-organizing teams — teams that manage themselves make better solutions.
  • Regularly reflect and adjust — teams pause often to improve how they work (retrospectives).

Roles in the startup mindset

  • Entrepreneur — an individual who establishes a new business venture.
  • Intrapreneur — an employee within a company who adopts an entrepreneurial mindset.
  • Extraneur — an individual within a company who performs tasks outside their formal role or responsibilities.

Agile frameworks

In December 2001 the Agile foundation launched a model known as the Agile model — a family of frameworks for applying it.

1 · Scrum

Best for: big projects, long-term development, and regular updates (typically spanning more than 3 years).
Used by: product-based companies focusing on iterative delivery and continuous improvement.

  • Divides work into time-boxed iterations called sprints (usually 2–4 weeks).
  • Defined roles: Product Owner, Scrum Master, and Development Team.
  • Emphasizes regular feedback, adaptive planning, and team collaboration.

2 · Kanban

Best for: small projects, short-term goals, and continuous delivery.
Used by: service-based companies prioritizing flexibility and workflow efficiency.

  • Visualizes work using a Kanban board (To Do, In Progress, Done).
  • Focuses on limiting work in progress (WIP) to improve flow and reduce bottlenecks.
  • Allows on-demand changes without fixed iterations.

3 · Extreme Programming (XP)

Best for: complex projects with frequently changing requirements where technical excellence is critical.

  • Promotes engineering best practices: pair programming, TDD, and continuous integration.
  • Encourages high customer involvement and rapid feedback loops.
  • Example: a startup building an innovative product with uncertain or fast-changing requirements.

4 · SAFe (Scaled Agile Framework)

Best for: scaling Agile practices across large organizations.
Used by: enterprises with multiple teams working on the same product or system.

  • Combines Agile, Lean, and DevOps principles to coordinate large-scale software development.
  • Structured approach for aligning teams, managing dependencies, and delivering value across the organization.
  • Similar to Scrum in its iterative nature, but designed for complex, multi-team scenarios.

01 · DevOps & SDLC

The Agile model

An iterative approach that breaks a project into small, manageable increments so teams can adapt to change quickly.

1

Plan — Requirements

Objective: define high-level requirements and prioritize features. Participants: product owners, business analysts, stakeholders. Create user stories and product backlogs; plan sprints and set iteration goals.

2

Design — architecture

Objective: create the technical design and architecture for the current iteration. Participants: architects, senior engineers, technical leads. Design system components and workflows; establish coding standards and design patterns (e.g., microservices, MVC).

3

Code — OOP

Objective: develop the software based on design specifications. Participants: developers and programmers. Write clean, modular code following Object-Oriented Programming (OOP) principles in languages like Java, .NET, Python, etc.; conduct code reviews and pair programming.

4

Test — quality gate

Objective: ensure the software meets requirements and is free of critical defects. Participants: QA engineers, testers, and sometimes developers. Perform functional, integration, and regression testing; testers may fix minor bugs directly while major issues escalate to developers; use automated testing tools for efficiency.

5

Release — multiple environments

Objective: prepare software for deployment across various environments. Participants: DevOps, release managers, operations teams. Environments include Dev (development and initial integration), Test (functional and integration testing), QA (quality assurance and UAT), Perf (performance and load testing — a 6-second response speed is the benchmark), Staging (pre-production mirror of production), Production (live), and DR Server (disaster recovery backup).

6

Deployment — Prod & DR

Objective: deploy to the live environment and ensure disaster recovery readiness. Participants: DevOps engineers, system administrators. Use CI/CD pipelines for automated deployment; keep production and DR environments synchronized for high availability.

7

Monitoring

Objective: continuously monitor performance and user experience post-deployment. Participants: DevOps, operations teams, support staff. Track system health, performance metrics, and error logs with tools like Prometheus, Grafana, Datadog, or New Relic; respond to incidents and optimize based on user feedback and system behavior.

Approval process before production

A formal approval chain is typically required before software moves from testing to production:

  1. Sponsor — usually a business or project stakeholder; ensures the software aligns with business goals and is ready for release.
  2. Architect — reviews technical design and infrastructure readiness; ensures the system is scalable, secure, and maintainable.
  3. Senior Engineer — validates implementation quality and resolves technical concerns; confirms the software meets performance and reliability standards.

If all three approve, the software completes User Acceptance Testing (UAT) and is moved to the production server.

Product transfer: Agile vs. DevOps

Agile approachDevOps approach
TransferManual — Build Engineer compiles and packages; Release Engineer manages deployment across environments; Production Engineer ensures the software runs correctly in production.Automated — the entire build, test, deploy, and monitor loop is automated using CI/CD pipelines.
AccountabilityEngineers are manually accountable for transferring the product between servers.Automation reduces human error and accelerates delivery; engineers focus on pipeline optimization and monitoring.
Tools—Jenkins, GitLab CI, Azure DevOps, GitHub Actions.

Types of release environments

Lower environments

Characteristics: no revenue impact or client access — used for development, testing, and quality assurance.

  • Dev Server — initial development and integration.
  • Test Server — functional and integration testing.
  • QA Server — quality assurance and bug fixing.

Higher environments

Characteristics: revenue-generating or client-accessible — closely monitored for performance, uptime, and security.

  • Production (Prod) — live environment used by end-users.
  • Performance (Perf) — used for load and stress testing; access limited to sponsors and technical teams, not accessible to end-users.
  • Disaster Recovery (DR) — backup environment for failover and recovery.
02 · Version Control

VCS: RCS → SCM → DVCS

Version control lets developers save, track, and manage their code — from centralized servers to distributed repos.

Version control is used by developers to keep track of their code — save · track · manage. It first appeared in the 1960s; everyone who uses code uses a VCS.
EVOLUTION OF VERSION CONTROL ├── 1960s RCS → Revision Control System ├── Agile SCM → Source Code Management (client-server) └── DevOps VCS → Version Control System (distributed)

RCS (1960s)

In the pre-agile era, code was written only on a single computer by each developer — an outdated concept. Client-server architecture was not yet introduced.

SCM (Source Code Management)

Client-server architecture is in use. Every developer writes their part of the code and sends it to a centralized server where every feature is merged.

SCM drawbacks

  • Requires being online.
  • Latency problem.
  • No encryption.
  • If the server is down, no work can be done.
  • Cannot use when offline.

DVCS (Distributed Version Control System)

Created by Linus Torvalds because of the drawbacks in SCM. There is a centralized repo on the server and a local repo on each developer's machine.

  • Each developer has their own local repo on their individual machine.
  • To push code to the remote repo, a developer first pushes to their local repo, then to the remote repo.
  • The data in the repo is encrypted.
  • Examples: Git, Tortoise, Mercurial, ClearCase.
Interview staple: the difference between centralized and distributed VCS.
Fun fact: there was no undo option before 1980.

Key terms

  • Repository — contains all the pieces of code written for the project.
  • Feature — when a project is being developed, developers are assigned to develop different parts; each part is also known as a feature.
02 · Version Control

Git

Git is an open-source VCS by Linus Torvalds — the first tool to implement DVCS.
  • Contains a remote repo and a local repo.
  • Encryption via SHA (Secure Hash Algorithm).
  • Available for Windows / Linux / macOS; supports 32-bit and 64-bit.
  • Released in 2003 by Linus Torvalds.
  • Written in C → Perl → Python.
  • No system requirements for installing Git.

Git architecture

WORKING DIRECTORY → STAGING AREA (git add) → LOCAL REPO (git commit) → REMOTE REPO (git push)

Files move from your working directory into the staging area, are committed to the local repository, then pushed to the shared remote repository — with SHA hashing keeping history tamper-evident.

Git commands

The day-to-day command set for configuring, staging, committing, and inspecting history.

1 · Configuration

bash 
git config --global --list                 # check configuration (user name, email, ...)
git config --global user.name "yourusername"
git config --global user.email "youremail"

2 · Initialize & commit

bash 
git init                       # create a project on your laptop
# create the file, edit it, save and exit
git add "filename"             # stage the file
git commit -m "message"        # commit it

3 · Status & staging

bash 
git status                     # check the status of git
git add "filename"             # stage a single file
git add "file1" "file2" ...    # stage multiple files
git add .                      # stage all files at once

4 · Committing

bash 
git commit -m "message"        # single file / all staged files
git commit -m "message" file1 file2   # specific files
git commit -m "message" .      # all staged files in the current directory

5 · Inspecting history

bash 
git show                      # show the latest commit on the current branch
git log                       # show all commits
git log --oneline             # one line per commit: id + message only
git revert <commit id>         # remove a commit and go back to the previous state
git ls-files                  # list files available in the commit area
Note: never revert the initial commit that created the file. A revert is itself stored as a new commit with its own commit id.

Authentication: tokens & keys

Tokens are like special passwords used to authenticate without using your real GitHub password — they provide secure access to repos, APIs, and CI/CD, with limited, revocable permissions.

TypeWhat it isWhere it is managed
Personal Access Token (PAT)Created manually. Classic PATs are older with wide permissions; fine-grained PATs are newer, repo-specific, and more secure. Used from the CLI and for automation.Settings → Developer settings → Personal access tokens
OAuth TokenCreated automatically when you sign in through an app (VS Code, GitHub CLI, GitHub Desktop); the app manages it for you.Settings → Applications → Authorized OAuth Apps
GitHub App TokenGenerated when a GitHub App is installed; apps use them to act with limited access.Settings → Applications → Installed GitHub Apps
SSH KeysPublic/private key pairs used instead of tokens for Git operations; password-less push/pull once configured.Settings → SSH and GPG keys

When to use what

  • OAuth Token → for apps (VS Code, GitHub Desktop, GitHub CLI).
  • PAT → for command-line usage, CI/CD pipelines, automation scripts.
  • SSH Keys → for developers who want password-less Git push/pull.
  • GitHub App Tokens → for integrations (bots, automation apps).

Security best practices

  • Always use least privilege (grant only required permissions).
  • Set expiration dates for PATs.
  • Store tokens securely (Password Manager, OS Keychain).
  • Revoke tokens immediately if exposed.
  • Prefer fine-grained PATs or OAuth over classic PATs.
In short: PAT = manual token you control · OAuth = automatic token apps control · SSH = key-based alternative · App tokens = for GitHub Apps/bots.
02 · Version Control

Git push & pull

git push

Send (upload) your local commits to a remote repository (e.g., GitHub), updating the remote branch with your local changes.

bash 
git push <remote> <branch>
git push origin main
  • origin → remote repo name (default is "origin").
  • main → branch name.
  • Only pushes commits that exist locally but not remotely.
  • Create a new remote branch with git push -u origin branch_name.
  • Use force (-f) carefully to overwrite remote history.

git pull

Fetch (download) changes from a remote repository and merge them into your local branch — basically a shortcut for git fetch + git merge.

bash 
git pull <remote> <branch>
git pull origin main
  • Downloads changes from origin/main and merges into the current branch.
  • Keeps your local branch up-to-date with the remote.
  • If conflicts exist, Git asks you to resolve them before merging.
  • git pull --rebase avoids merge commits (reapplies your commits on top of the updated remote branch).

Common workflow

bash 
# 1. Make changes locally
git add .
git commit -m "Message"

# 2. Get the latest updates
git pull origin main

# 3. Push your changes
git push origin main

Differences

CommandAction
git pushUploads local commits → remote repo
git pullDownloads + merges remote commits → local repo

Best practices

  • Always run git pull before git push (to avoid conflicts).
  • Use git status to check branch state before pushing/pulling.
  • Avoid git push -f unless you know what you are doing.
  • Use git pull --rebase for cleaner history.

Git branching

A branch is a separate line of development — isolation, collaboration, and clean history.

By default a repository starts with a main branch (main or master). Branching lets multiple developers work on different features or bug fixes without interfering with each other, and keeps main safe.

main ├── feature/login ├── feature/cart ├── bugfix/login-error ├── release/v1.0 └── hotfix/security-patch

Common branch commands

bash 
git branch branch_name            # create a branch
git checkout branch_name         # switch to a branch
git switch branch_name           # modern way to switch
git checkout -b branch_name      # create + switch in one step
git switch -c branch_name        # modern create + switch

git branch                       # list branches (* = current branch)
git checkout main
git merge branch_name            # merge a branch into main
git branch -d branch_name        # safe delete (only if merged)
git branch -D branch_name        # force delete
git push origin branch_name      # push a branch to remote

Branching workflow examples

WorkflowUse caseExample names
Feature branchingNew featuresfeature/login, feature/cart
Bugfix branchingSmall fixesbugfix/login-error
Release branchingPreparing stable releasesrelease/v1.0
Hotfix branchingUrgent fixes on productionhotfix/security-patch

Best practices

  • Always create a new branch for features/bugs — do not code directly on main.
  • Use meaningful branch names (feature/auth-system, not test123).
  • Keep branches short-lived to avoid conflicts.
  • Regularly pull updates from main to keep your branch up-to-date.
  • Delete merged branches to keep the repo clean.
Note: whenever you create or move branches, always check git status first — it should be clean.

03 · CI/CD & Build

The Jenkins CI process

From a developer commit to packaged artifacts, feedback, and optional deployment.

graph LR A[Developer Commit] --> B[Jenkins Trigger] B --> C[Source Code Checkout] C --> D[Build] D --> E[Automated Testing] E -->|tests fail| N[Notify team & stop] E -->|tests pass| F[Code Analysis] F --> G[Packaging & Artifacts] G --> H[Deployment] H --> I[Feedback & Notifications]

1 · Developer commit

A developer writes code and pushes it to a version control system (e.g., GitHub, GitLab, Bitbucket).

2 · Jenkins trigger

Jenkins is connected to the repository via a webhook or polling; new code automatically triggers a build job.

3 · Source code checkout

Jenkins pulls the latest code from the repository.

4 · Build process

Build tools like Maven, Gradle, Ant, npm compile the code and build the project.

5 · Automated testing

Unit tests, integration tests, or other automated suites run. Pass → pipeline continues; fail → Jenkins notifies the team and stops.

6 · Code analysis

Optional: static code analysis tools (like SonarQube) check code quality and security issues.

7 · Packaging & artifacts

On success, the code is packaged (e.g., .jar, .war, .zip, Docker image) and stored in a repository like Nexus, Artifactory, or Docker Hub.

8 · Deployment

Optional CD step: deploy automatically to a development server, staging environment, or production (if Continuous Delivery/Deployment is enabled).

9 · Feedback & notifications

Jenkins sends results (success/failure) via email, Slack, or dashboards so developers get quick feedback.

Simplified Jenkins CI pipeline flow

Commit → Jenkins Trigger → Build → Test → Package → Deploy (optional) → Feedback

Artifact

An artifact is a piece of software code that is compiled, built, tested, and packaged. In Jenkins, an artifact is the file or set of files created when a program is built — a program (.exe), a package, or reports. Jenkins saves them so they can be used later for testing, sharing, or putting the program into use, without rebuilding everything again.

03 · CI/CD & Build

Maven

A build automation and project management tool primarily used for Java-based projects.

Maven simplifies building, testing, packaging, and managing Java applications through standardized conventions and automation. It uses an XML file called pom.xml (Project Object Model) to configure project settings, dependencies, and build instructions.

Key features

  • Dependency management — automatically downloads and manages external libraries.
  • Standard project structure — consistent folder layout for source, tests, and resources.
  • Build lifecycle — predefined phases: compile, test, package, deploy.
  • Plugins — rich ecosystem for compiling, testing, reporting, and more.
  • Repositories — downloads dependencies from central or remote repositories and caches them locally.
  • Build profiles — customizes builds for different environments (development, testing, production).

Benefits

  • Streamlines the build process with minimal manual intervention.
  • Encourages best practices and consistency across projects.
  • Standardizes project structure and dependency management for easier collaboration.
  • Generates project documentation and reports automatically.
  • Integrates with IDEs (Eclipse, IntelliJ, VSCode) and CI/CD tools like Jenkins.

04 · Containers

Virtualization & its limits

Running different operating systems on the same hardware — and why that gets heavy.

Virtualization

  • Came into use in the year 2000, invented by VMware.
  • All about running different OSes on the same hardware.
  • Types: bare metal and hosted.
  • Benefits: cost cutting, scaling, efficient use of resources.

Drawbacks of virtualization

Heavy resource overhead

VMs require a full guest OS per instance, consuming significant CPU, memory, and disk — limiting scalability and slowing boot times.

Slow startup & shutdown

VMs initialize an entire OS to start. Containers start almost instantly because they share the host OS kernel.

Limited portability

VM images are tightly coupled to hypervisors and host configurations; Docker containers are portable across cloud, local, and CI/CD environments via standardized images.

Complex configuration & maintenance

Managing VMs means configuring hypervisors, networking, storage, and OS updates; Docker simplifies this with declarative Dockerfiles and isolated environments.

Inefficient DevOps workflows

VMs are less suited to rapid iteration, testing, and deployment; Docker enables reproducible builds, versioned containers, and seamless CI/CD integration.

Security isolation trade-offs

VMs offer strong isolation via hardware abstraction but are slower and harder to patch; Docker uses process-level isolation — faster but needing careful security practices.

04 · Containers

Docker core concepts

Docker is an open-source platform that automates the deployment, scaling, and management of containerized applications.

What Docker provides

  • Docker Engine — the runtime that builds and runs containers.
  • Docker Images — read-only templates used to create containers.
  • Dockerfile — a script that defines how to build a Docker image.
  • Docker Hub — a registry for sharing and downloading container images.
  • Docker Compose — defines and runs multi-container applications.

Docker has 2 versions: a free version and a paid Enterprise version.

Real-world analogy

Containers are like shipping containers: no matter what's inside (cars, electronics, clothes), they're standardized and can be transported by ship, train, or truck. Docker is the system that builds, loads, and moves those containers efficiently.

The building blocks

1

Image

A read-only template used to create containers — the blueprint. Contains the application and all dependencies (e.g., ubuntu:22.04, or a custom image built for your web app).

2

Container

A runnable instance of an image — a lightweight, isolated process on the host kernel. You can start, stop, and delete them. If the image is a class, the container is an object.

3

Dockerfile

A text file with instructions for building a Docker image — the recipe that automates image creation.

4

Docker Daemon

The background service on the host that manages building, running, and distributing containers — it does the heavy lifting.

5

Docker Client

The CLI tool (docker) you use to talk to the daemon. docker run sends the command to the daemon, which executes it.

6

Registry

A storage system for Docker images — the most common public one is Docker Hub, like an app store for images. You can pull images from it and push your own.

Role of DevOps engineers

  • Creation of images.
  • Maintaining containers — this can be automated by Kubernetes.

Installing Docker

  • Requires a Linux kernel version ≥ 3.10.
  • Create a virtual machine to install Docker on.

About the Dockerfile

  • Helps us create images — it contains the instructions.

06 · Config Management

Configuration management

Configuration management was first introduced by the Puppet tool. Its main focus is deployment — keeping systems consistent and controlling the deployment tool's configuration file.

What configuration management does

  • Checks whether an application is deployed or not.
  • Checks for any deviations after deployment.
  • Sends alerts to the user.
  • Configurations are managed by a configuration file.
  • Helps quickly fix problems.
  • Configuration management code is written to manage; you can also write code to check the configurations.

If someone changes the configuration file

  1. Restart the server — on boot it checks the default config; if deviations are found, it discards the changes and reverts to default.
  2. Rerun the configuration file.
Key point: the deployment tool controls the whole configuration file — after it is deployed, no one can change it.

06 · Config Management

How Ansible works

Ansible's magic lies in simplicity — agentless, idempotent, and SSH-based.

Agentless

Needs no special software on the servers it manages — it uses a standard protocol already present on almost every server: SSH (Linux) or WinRM (Windows).

Idempotent

Running an Ansible task multiple times always produces the same result. If a task ensures a web server is installed, running it once installs it; running it again does nothing because the server is already there — making Ansible safe, predictable, and reliable.

The Ansible automation cycle

graph LR A[Control Machine] --> B[Playbooks + Inventory] B --> C[SSH connection] C --> D[Managed Nodes] D --> E[Modules run & clean up] E --> F[Results back to Control Machine]
1

Control Machine

The only place Ansible needs to be installed. From here you write Playbooks, define the Inventory, and run ansible-playbook.

2

Playbooks

The heart of Ansible — a YAML file containing tasks to execute. Human-readable and declarative: you declare the desired state of the system, not the step-by-step process. Example: "I want the Nginx web server to be running."

3

Inventory

A simple file (usually INI or YAML) listing all servers (nodes or hosts) to manage, which can be grouped for easier management.

4

SSH connection

When you run a playbook, the control machine uses SSH to connect to each node, authenticating with SSH keys or passwords. No agents to install on target servers.

5

Managed nodes

The target servers to configure — physical servers, VMs, or cloud instances, reachable via SSH.

6

Modules

Ansible uses small, single-purpose programs called modules (pushed to the node) instead of running commands directly. After a module runs it is removed, keeping nodes clean. Examples: yum/apt (packages), service (services), copy (files), user (accounts), git (repos).

Example playbook & inventory

playbook.yml 
---
- name: Ensure web server is running
  hosts: webservers
  tasks:
    - name: Install the latest version of Apache
      ansible.builtin.yum:
        name: httpd
        state: latest

    - name: Make sure Apache is running
      ansible.builtin.service:
        name: httpd
        state: started
inventory 
[webservers]

Steps to create the Ansible server

Playbooks & YAML

Playbooks are YAML files defining a sequence of tasks to be executed on managed nodes — automating configurations, deployments, and orchestrations. Playbooks use modules to carry out tasks.

YAML essentials

  • To write playbooks in Ansible, YML is used — file extension .yml or .yaml.
  • Three core concepts: key-value pairs, lists, and maps. Lists follow the order of elements.
  • Playbooks contain the deployment script — written on the server, executed from the server, implemented on the client.

Playbook structure

  • Should start with a hyphen (-), with a single space of indentation.
  • name: — the name of the playbook.
  • hosts: all — addresses of all hosts on which the implementation should be done; all indicates every available host.
  • tasks: — each task starts with a hyphen and can be named; each uses a module.

Flow of Ansible execution

write playbooks in VSCode → push to GitHub → pull the repo in the Ansible server → implement on the client

Execute a playbook

bash 
ansible-playbook <playbook_name> -i <location of inventory file>
ansible-playbook <playbook_name> -i <location> --check   # dry-run: verify the playbook is correct
Steps to create and execute a playbook: write the code in VSCode → commit and push to GitHub → pull the repo in the Ansible server → run with --check (inventory at /etc/ansible/hosts) → run the command to execute the playbook.

Example playbooks

create a directory on the client 
---
- name: sample playbook
  hosts: all
  tasks:
    - name: module1
      command:
        cmd: mkdir /opt/vnr-b3
install git 
---
- name: installing git
  hosts: all
  tasks:
    - name: code to install git
      yum:
        name: git
        state: present
multiple tasks 
---
- name: create directory
  hosts: all
  tasks:
    - name: create directory
      command:
        cmd: mkdir /opt/hyderabad

    - name: creating text file
      command:
        cmd: touch /opt/hyderabad/india.txt
file module 
---
- name: Create a folder named asia and a file named delhi.txt
  hosts: all
  become: yes
  tasks:
    - name: Create the folder 'asia'
      file:
        path: /opt/asia
        state: directory
        mode: '0755'

    - name: Create the file 'delhi.txt' inside asia folder
      file:
        path: /opt/asia/delhi.txt
        state: touch
        mode: '0644'
lineinfile module 
---
- name: Create folder 'university' and file 'vnr.txt' with a line using lineinfile
  hosts: all
  tasks:
    - name: Create the folder 'university'
      file:
        path: /opt/university
        state: directory

    - name: Ensure the file 'vnr.txt' exists
      file:
        path: /opt/university/vnr.txt

---
- name: Replace text and install software
  hosts: client
  become: yes
  tasks:

        replace: 'hello world'

06 · Config Management

Config management deep dive

Clarifying the core goals behind configuration management and how Ansible enforces them.

The real focus of configuration management

While deployment is an outcome of good configuration management, the primary goals are:

  1. Automate the setup and maintenance of systems.
  2. Enforce consistency across all environments (dev, staging, production).
  3. Prevent "configuration drift" — when servers become different from each other over time due to manual changes.

Declarative & idempotent

A playbook task like state: present ensures an application is deployed. Ansible checks the current state: if already present it does nothing; if missing, it deploys it.

Preventing configuration drift

If someone manually changes a config file, the next playbook run detects the deviation and reverts the server to the correct state defined in the code.

Alerting

Ansible has no built-in alerting like a monitoring tool (Prometheus or Datadog), but it integrates — modules like mail or uri can send email or call a webhook (e.g., Slack, PagerDuty) on failure or change.

Infrastructure as Code

The playbook is the configuration file — the single source of truth. Store it in version control (Git) for history, code reviews, and an audit trail. This practice is known as Infrastructure as Code (IaC).

Fast recovery

If a server fails, provision a new blank server and run the playbook against it — in minutes you have an identical, fully configured replacement, speeding up disaster recovery.

Verification tooling

ansible-playbook --check simulates a run ("dry run") and reports what would change; Ansible Lint checks playbooks for best practices and errors; Molecule tests Ansible roles.
