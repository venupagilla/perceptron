Cloud computing, IAM & Linux

Cloud computing models, AWS identity and access management, security groups, and the Linux command line that drives EC2.

Cloud computing

Cloud computing is the on-demand supply of IT resources on rent — you provision compute, storage, and networking as you need them instead of buying and maintaining physical hardware.

Advantages of cloud computing

  • Cost — pay only for what you use
  • Availability — resources are accessible whenever needed
  • Reliability — services continue to work despite failures
  • Security — built-in protections and compliance controls
  • Market place — pre-built services and solutions ready to use
  • Connectivity — global reach from anywhere

Job roles

Cloud engineer

Builds and maintains cloud infrastructure.

Cloud developer

Develops applications that run in the cloud.

Cloud architect

Designs the overall cloud solutions and topology.

Virtualization

Virtualization is the process of turning physical hardware into a software environment — it is the foundation that lets one physical server run many isolated virtual machines.

List down 50 cloud computing companies.

Types of cloud computing

PaaS — Platform as a Service

Renting a complete development environment over the internet. You get a platform to build, run, and manage applications, with tools for database integration, testing, and deployment — without worrying about infrastructure maintenance.

Examples: Heroku, Google App Engine.

SaaS — Software as a Service

Renting software over the internet instead of installing it locally. You get applications accessible through a browser; updates, bug fixes, and new features are handled by the provider.

Examples: Google Workspace (formerly G Suite), Salesforce.

IaaS — Infrastructure as a Service

Renting the basic building blocks of a computer over the internet: virtual machines or servers, storage space, and networking components like firewalls and load balancers. You manage the OS, apps, and data on top.

Examples: Amazon EC2, Google Compute Engine.

Who manages what

Moving from IaaS to SaaS shifts management responsibility to the provider: IaaS — you manage OS/apps/data; PaaS — provider manages the platform, you manage your app; SaaS — provider manages everything.

IAM — Identity and Access Management

What IAM is

AWS provides an Identity and Access Management (IAM) system that enables you to manage access to your AWS services and resources securely.

Benefits of IAM users

  • Security Best Practices — avoid using the root user and reduce security risks
  • Granular Access Control — assign specific permissions using policies
  • Multi-Factor Authentication (MFA) — add an extra layer of security
  • Group and Role Management — organize users into groups and assign roles
  • Auditing and Monitoring — track activities using AWS CloudTrail
  • Temporary Credentials for Applications — use IAM roles for secure access
  • Least Privilege Access — grant only necessary permissions to users

Steps to create an IAM user

  1. Open the IAM dashboard
  2. Click on Users
  3. Click on Create user and specify a username
  4. Check "Provide user access to the AWS Management Console" (optional)
  5. Click on "I want to create an IAM user"
  6. Set a password — two options: autogenerated or custom
  7. Optionally check "Users must create a new password at next sign-in"
  8. Click Next — you are redirected to the set-permissions page
  9. Three options: Add user to group, Copy permissions, or Attach policies directly
  10. Click on Attach policies directly
  11. Search for the policy you want to add, e.g. AdministratorAccess
  12. Click Next — you are redirected to the review page
  13. Review and click Create user
  14. Save the password as a CSV, and optionally send it as a mail with the instructions

Login as an IAM user

  1. Open the IAM user login page
  2. Required fields:
    • 12-digit account ID
    • Username
    • Password

Benefits of IAM user groups

  • Simplified Management — manage multiple users at once by assigning permissions to a group instead of individual users
  • Consistent Access Control — ensure all users in a group have uniform permissions, reducing misconfigurations
  • Easier Policy Updates — modify permissions at the group level instead of updating each user separately
  • Scalability — easily add or remove users from groups without affecting security policies
  • Least Privilege Principle — assign only necessary permissions to groups, improving security
  • Improved Compliance — maintain structured access control for audits and security compliance
  • Role-Based Access Control (RBAC) — organize users into logical groups like Admins, Developers, or Viewers
  • Reduced Risk of Human Error — centralized control minimizes accidental over-permissions

Steps to create an IAM user group

  1. Click on User groups in the IAM dashboard
  2. Click on Create group
  3. Give a name for the user group
  4. Select the users you want to add to the group
  5. Add the policies
  6. Click on Create

Roles

Roles are identities that define permissions for accessing AWS services. Roles are similar to users, but they don't have permanent credentials — instead, they create temporary security credentials when needed.

Steps to create a role

  1. Select Roles from the IAM dashboard
  2. Click on Create role
  3. Select the trusted entity type and use case, then click Next
  4. Give permissions and click Next
  5. Give a role name, description, etc., and click Create role

Policies

Policies are JSON-based documents that define permissions and control access to AWS resources. They specify who (users, groups, or roles) can perform what actions on which resources, and under what conditions.

Types of policies

  • AWS policies (managed by AWS)
  • User-created policies (custom)

Security groups

Definition

A Security Group (SG) in AWS acts as a virtual firewall that controls inbound and outbound traffic for EC2 instances and other AWS resources. It helps define which IP addresses and ports are allowed to connect to your instance.

Important points about security groups

  • Acts as a virtual firewall controlling inbound and outbound traffic for EC2 and other AWS resources
  • Stateful — if an incoming request is allowed, the response is automatically allowed without an explicit outbound rule
  • Only allow rules — security groups do not support deny rules (unlike Network ACLs)
  • Attached to instances, not subnets — assigned to individual EC2 instances, not entire subnets
  • Can have multiple security groups — an instance can have several applied at once
  • Default security group — if none is specified, AWS assigns one that allows all outbound traffic and blocks all inbound traffic
  • Rules use protocols & ports — rules specify protocols (TCP, UDP, ICMP), port numbers (e.g. 22 for SSH, 80 for HTTP), and IP ranges (CIDR) or another security group as source/destination
  • Supports cross-security-group communication — allow traffic between instances by specifying another security group as the source
  • Applies to several AWS services — used with EC2, RDS, Lambda (VPC-enabled), ELB, and more
  • Modifications take effect immediately — changes apply instantly without restarting instances

Elastic Block Storage (EBS)

What block storage is

Block storage is a type of data storage commonly used in cloud computing and enterprise IT environments. Data is divided into fixed-sized chunks or "blocks", which are stored separately and assigned unique identifiers. These blocks can be accessed and managed independently, allowing for efficient data retrieval and flexibility.

EBS is a zonal service — it is tied to a specific availability zone within a region.

Performance metrics of a hard disk

Throughput

Measures how much data can be read from or written to a storage device, typically expressed in MB/s (Megabytes per second) or Gbps (Gigabits per second).

Input/Output Operations Per Second — the number of read and write operations a storage device can perform in a second.

Measures the probability of data being safely stored and not lost or corrupted over time.

Networking — IP, subnetting & VPC

IP address classes, private ranges, subnetting and CIDR, networking components, and VPC peering on AWS's backbone.

IP address classes

IP addresses are divided into five classes based on the first octet (the first number in the IP). These classes were originally designed to allocate address spaces efficiently.

ClassRangeFirst Octet BitsPurposeDefault Subnet Mask
A0.0.0.0 – 127.255.255.2550xxxxxxxLarge networks (e.g. ISPs)255.0.0.0 (/8)
B128.0.0.0 – 191.255.255.25510xxxxxxMedium networks (e.g. companies)255.255.0.0 (/16)
C192.0.0.0 – 223.255.255.255110xxxxxSmall networks (e.g. LANs)255.255.255.0 (/24)
D224.0.0.0 – 239.255.255.2551110xxxxMulticasting (e.g. streaming)None (not subnetted)
E240.0.0.0 – 255.255.255.2551111xxxxResearch and developmentNone (not subnetted)

Additional notes on classes

  • Classful addressing — this system (Classes A–E) is largely historical. Modern networking uses Classless Inter-Domain Routing (CIDR), which allows flexible subnet masks instead of fixed class boundaries.
  • Reserved IPs in Class A — 0.0.0.0 (default network, "any"/"unknown") and 127.0.0.0 – 127.255.255.255 (loopback range; 127.0.0.1 is localhost).
  • Class D — used for multicast groups (e.g. video conferencing, IPTV); devices subscribe to these addresses rather than being assigned them.
  • Class E — experimental; not used in public or private networks.

Usable public IP ranges

These exclude reserved addresses:

  • Class A: 1.0.0.0 – 126.255.255.255
  • Class B: 128.0.0.0 – 191.255.255.255
  • Class C: 192.0.0.0 – 223.255.255.255

Private IP ranges

Private IPs are reserved for internal networks (e.g. home or office LANs) and are not routable on the public internet. They require Network Address Translation (NAT) to communicate externally. Defined in RFC 1918.

ClassRangeNumber of IPs
A10.0.0.0 – 10.255.255.25516,777,216 (1 network)
B172.16.0.0 – 172.31.255.2551,048,576 (16 networks)
C192.168.0.0 – 192.168.255.25565,536 (256 networks)
  • Class A — large enterprises (e.g. 10.x.x.x)
  • Class B — medium-sized organizations (e.g. 172.16.x.x)
  • Class C — home networks (e.g. 192.168.1.x)
  • NAT — routers translate private IPs to public IPs for internet access

Subnetting & CIDR

Subnetting divides a larger network into smaller subnetworks, improving efficiency and security. The subnet mask defines which part of the IP is the network and which is the host.

ClassDefault Subnet MaskCIDRFormatTotal IPsUsable Hosts
A255.0.0.0/8n.h.h.h16,777,21616,777,214
B255.255.0.0/16n.n.h.h65,53665,534
C255.255.255.0/24n.n.n.h256254
  • n = Network portion, h = Host portion
  • Total IPs — calculated as 2^(32 − CIDR bits)
  • Usable Hosts — total IPs minus 2 (network address and broadcast address). Example: /24 = 256 IPs, but 254 usable (network: x.x.x.0, broadcast: x.x.x.255).
  • Binary — /8 means first 8 bits are network (255.0.0.0); /16 means first 16 bits (255.255.0.0); /24 means first 24 bits (255.255.255.0).

Practical subnetting example

IP: 192.168.1.0/24

  • Network: 192.168.1.0
  • Broadcast: 192.168.1.255
  • Usable range: 192.168.1.1 – 192.168.1.254

Smaller subnet: 192.168.1.0/26 — /26 = 32 − 26 = 6 host bits → 2⁶ = 64 IPs per subnet.

  • Subnets: 192.168.1.0/26, 192.168.1.64/26, 192.168.1.128/26, 192.168.1.192/26
  • Usable hosts per subnet: 62 (64 − 2)

Why Class A isn't used practically without subnetting

  • Broadcast traffic overload
  • Lack of segmentation (security and organization)
  • Need for network and broadcast addresses

16+ million hosts in a single network is simply unmanageable.

CIDR examples

CIDR 10.0.0.0/16

  • Network bits: 16 (first 2 bytes)
  • Range: 10.0.0.0 – 10.0.255.255
  • Total IPs: 65,536 (2¹⁶)
  • Usable hosts: 65,534

Subnet 10.0.1.0/24

  • Network bits: 24 (first 3 bytes)
  • Range: 10.0.1.0 – 10.0.1.255
  • Total IPs: 256 (2⁸)
  • Usable hosts: 254
CIDR vs. classful: CIDR (Classless Inter-Domain Routing) uses variable-length subnet masks for flexibility — it allows borrowing bits from the host portion to create more networks (e.g. /20 instead of /16).

Additional notes

  • IPv4 vs. IPv6 — IPv4 is 32-bit (4 billion addresses, nearly exhausted); IPv6 is 128-bit (e.g. 2001:0db8::1), designed to replace IPv4 due to address scarcity.
  • Loopback — 127.0.0.1 is used to test network functionality on the local machine.
  • APIPA (Automatic Private IP Addressing) — range 169.254.0.0 – 169.254.255.255, assigned automatically when DHCP fails.
  • Broadcast — traffic sent to all devices in a subnet (e.g. 192.168.1.255 for /24).

Peering connections

Peering in general

A peering connection is a direct network link between two separate networks to exchange traffic efficiently, bypassing the public internet. It's typically used to reduce latency, improve bandwidth, and enhance security by avoiding third-party intermediaries.

  • Two autonomous networks (e.g. two companies, ISPs, or cloud providers) agree to connect their infrastructure.
  • Traffic flows directly between them via a private link, often through a shared router or switch.
  • Public peering — via an Internet Exchange Point (IXP), where multiple networks connect.
  • Private peering — a dedicated, point-to-point link between two networks.

Example (general)

Company A (an e-commerce site) and Company B (a content delivery network, CDN) want to share data. Without peering, traffic goes through multiple public internet hops (e.g. 50 ms). With peering, a direct fiber link lets traffic flow directly (e.g. 5 ms), avoiding congestion. Streaming services like Netflix peer with ISPs to deliver content faster.

Benefits

  • Lower latency
  • Higher bandwidth
  • Cost savings (less reliance on transit providers)
  • Improved reliability

Limitations

  • Requires mutual agreement and compatible infrastructure
  • Doesn't inherently provide internet access — only connects the peered networks

VPC peering in AWS

In AWS, a VPC Peering Connection links two Virtual Private Clouds (VPCs) to route traffic privately using AWS's backbone network. It enables communication between two VPCs (same or different AWS accounts/regions). VPCs must have non-overlapping CIDR blocks (e.g. VPC A: 10.0.0.0/16, VPC B: 172.16.0.0/16).

Setup

  1. Create a peering request from the owner of VPC A
  2. Accept the request from VPC B's owner
  3. Update route tables in both VPCs to point to the peering connection (e.g. 10.0.0.0/16 → pcx-12345)
flowchart LR subgraph A["VPC A — 10.0.1.0/24 (Application)"] App[Web App] end subgraph B["VPC B — 172.16.1.0/24 (Database)"] DB[Database] end App <-->|"pcx-abc123 | private, AWS backbone"| DB

Result: the app in VPC A queries the database in VPC B privately over AWS's network — no internet gateway needed. Traffic uses private IP addresses.

Limitations

  • No transitive peering — if VPC A peers with B, and B peers with C, A can't reach C directly
  • Maximum of 125 peering connections per VPC (adjustable via quota request)
  • Doesn't support overlapping security groups or edge-to-edge routing (e.g. a NAT Gateway in one VPC can't serve the other)

Use case

Connect a web app VPC (10.0.0.0/16) to a database VPC (172.16.0.0/16) for secure, low-latency access.

Cost

Free within the same region; charges apply for cross-region peering (data transfer fees).

A gateway is the IP address given to a router interface where the network is connected.

Classful network

Advantages of creating subnets

Load balancing & auto scaling

Distributing traffic across servers and automatically adjusting capacity with Elastic Load Balancing and Auto Scaling.

Load balancing

Distribution of network traffic to multiple servers is known as load balancing. In AWS this is done automatically by the Elastic Load Balancing (ELB) service.

Auto scaling

Auto Scaling in AWS is a powerful feature that automatically adjusts the number of instances in your application based on demand.

Key advantages

  • Improved Availability — always has the right capacity for incoming traffic, reducing downtime and improving reliability
  • Cost Optimization — scales down resources during low-demand periods, saving costs by only using what is needed
  • High Performance — responds to demand spikes by rapidly adding instances, maintaining performance under heavy load
  • Fault Tolerance — replaces unhealthy instances with new ones, keeping the application running smoothly
  • Scalability — easily handles fluctuating workloads, ideal for unpredictable traffic or seasonal spikes
  • Ease of Management — automatically adjusts resources once configured, reducing manual intervention

Setting up auto scaling

  1. Create a Launch Template — define the EC2 configuration including the Amazon Machine Image (AMI), instance type, key pair, and security groups.
  2. Create an Auto Scaling Group — specify the launch template, desired capacity, minimum and maximum instances, and the VPC/subnet where instances run.
  3. Set Scaling Policies — define rules for scaling in/out based on metrics like CPU utilization, network traffic, or custom CloudWatch alarms.
  4. Test the Setup — simulate traffic or terminate instances to ensure Auto Scaling responds correctly.

Scaling models

Vertical vs. horizontal scaling

Vertical Scaling (Scaling Up)

Adding more power (CPU, RAM, or storage) to a single server or machine.

  • How: upgrade existing hardware or switch to a more powerful machine
  • Advantages: simpler to implement; fewer machines to manage
  • Drawbacks: limited by hardware capacity; downtime may be required for upgrades
  • Example: EC2 t2.micro → t2.large

Horizontal Scaling (Scaling Out)

Adding more machines or servers to distribute the workload across multiple systems.

  • How: add additional instances or nodes instead of upgrading hardware
  • Advantages: virtually unlimited scalability; redundancy improves fault tolerance
  • Drawbacks: more complex to set up and manage; apps may need to be designed for load distribution
  • Example: more EC2 instances in an Auto Scaling Group behind an ELB
Summary: vertical scaling improves the capacity of a single machine; horizontal scaling increases capacity by adding more machines. The choice depends on your workload, budget, and system design.

Scale In and Scale Out

Scale Out (Adding resources)

Increasing the number of instances, servers, or machines to handle higher loads.

  • Example: adding EC2 instances during traffic spikes
  • Use case: sudden increase in demand — ensures capacity without compromising performance

Scale In (Removing resources)

Decreasing the number of instances, servers, or machines during periods of low demand.

  • Example: terminating unused EC2 instances to reduce costs
  • Use case: off-peak hours — minimizes unnecessary usage, saving money while maintaining efficiency
Key advantage: the combination of Scale In and Scale Out achieves elasticity — infrastructure dynamically adjusts to match the workload, ensuring optimal performance and cost-effectiveness.

Amazon Machine Image (AMI)

In AWS, an image typically refers to an Amazon Machine Image (AMI) — a pre-configured template that contains the software, operating system, and settings required to launch an EC2 instance. It serves as the blueprint for creating virtual machines in the cloud.

Key features of AMIs

  • Customizable — create your own AMI by customizing an EC2 instance and saving it as an image
  • Region-specific — tied to specific AWS regions, but can be copied across regions
  • Types — AWS provides public AMIs, shared AMIs, and marketplace AMIs for various use cases

AMIs simplify deployment by allowing you to launch multiple instances with the same configuration.
