Language models

Language models are AI systems designed to process, generate, and understand natural language text.

Text → [ Language model ] → Text

There are two types:

LLMs

General-purpose models used for raw text generation. They take a string as input and generate text as output.

Chat Models

Language models specialized for conversational tasks. They take a sequence of messages as input and return chat messages as output.

Getting a response: invoke & messages

You can get a response from a model using the invoke, stream, or batch methods.

1Invoke method

The invoke method takes a single message or a list of messages representing a conversation history and responds with a single response at once, after it is entirely generated.

python 
from langchain_groq import ChatGroq
import dotenv

dotenv.load_dotenv()  # for importing system variables
model = ChatGroq(model="groq/gpt-oss-12ob")
model_resp = model.invoke("hi, how are you")
print(model_resp.content)

2Messages

Messages are structured objects used to communicate with Chat Models. For passing a conversation you can use either dictionaries or message objects.

Why use messages? they help maintain conversation history, allow setting behavior using a System Message, are more powerful and structured than raw text, and are required for ChatPromptTemplate.

Using a dictionary

python 
conv = [
    {"role": "system", "content": "you are a teacher"},
    {"role": "user", "content": "hi"},

    {"role": "user", "content": "teach me Algebra"}

python 
from langchain.messages import HumanMessage, AIMessage, SystemMessage

conv = [
    SystemMessage("M1"),

02 · Models

Stream & batch

1Stream

Most models can stream their output content while it is being generated. Calling stream() returns an iterator that yields output chunks as they are produced.

python 
for chunk in model.stream("why do parrots fly?"):
    print(chunk.text, end="", flush=True)
    # if we set flush to True the chunk prints right away

2Batch

Batching a collection of independent requests to a model can significantly improve performance and reduce costs, as the processing can be done in parallel.

python 
resp = model.batch([
    "ques 1",
    "ques 2",
    "ques 3"
])
for response in resp:
    print(response)

By default batch() only returns the final output for the entire batch. To receive output for each item as it finishes generating, stream results with batch_as_completed():

python 
for resp in model.batch_as_completed(["q1", "q2", "q3"]):
    print(resp)

These models are mostly released on Hugging Face and can be used via the langchain_huggingface package. There are two ways to use them.

Using a Hugging Face endpoint

HuggingFaceEndpoint is the recommended way in modern LangChain to access and run open-source models hosted on Hugging Face servers (no need to download the model locally).

  • Runs models remotely on Hugging Face's infrastructure.
  • Uses the serverless Inference API (free tier available with limits) or dedicated Inference Endpoints.
  • Very easy to switch between different open-source models.
python 
from langchain_huggingface import HuggingFaceEndpoint
import os
from dotenv import load_dotenv

load_dotenv()
os.environ["HUGGINGFACEHUB_API_TOKEN"] = "hf_xxxx"   # Your HF token

llm = HuggingFaceEndpoint(
    repo_id="meta-llama/Meta-Llama-3-8B-Instruct",  # or any other model
    task="text-generation",
    max_new_tokens=512,
    temperature=0.7,
    do_sample=True,
    # provider="auto"   # optional
)

response = llm.invoke("What is LangChain?")
print(response)

If you just want a simple text response this is fine — but to use it as a chat model and get the response in a LangChain-compatible format like an AIMessage, wrap the model in ChatHuggingFace first:

python 
from langchain_huggingface import HuggingFaceEndpoint, ChatHuggingFace

llm = HuggingFaceEndpoint(
    repo_id="meta-llama/Meta-Llama-3-8B-Instruct",
    task="text-generation",
    max_new_tokens=512,
    temperature=0.7
)

chat_model = ChatHuggingFace(llm=llm)   # this wrapper

response = chat_model.invoke("Hello, how are you?")
print(response.content)

Downloading models directly to run locally

This method downloads the full model weights to your machine and runs them on your own hardware (CPU/GPU). The main class used is HuggingFacePipeline (from langchain_huggingface).

python 
from langchain_huggingface import HuggingFacePipeline
from transformers import pipeline

# Create pipeline from downloaded model
pipe = pipeline(
    "text-generation",
    model="meta-llama/Meta-Llama-3-8B-Instruct",   # or smaller model like "gpt2", "TinyLlama/TinyLlama-1.1B"
    device=0,          # 0 for GPU, -1 for CPU
    max_new_tokens=512,
    temperature=0.7,
)

llm = HuggingFacePipeline(pipeline=pipe)

response = llm.invoke("What is LangChain?")
print(response)

For chat-style (recommended)

python 
from langchain_huggingface import ChatHuggingFace

chat_model = ChatHuggingFace(llm=llm)
response = chat_model.invoke("Hello, how are you?")

  • Installed libraries: transformers, torch, accelerate, langchain_huggingface.
  • First run will download the model (can take time and disk space).

Pros

  • Full privacy, offline, no rate limits.

Cons

  • Needs strong hardware, slower setup.
02 · Models

Embedding models

Embedding models convert text into numerical vectors (high-dimensional arrays) that capture the semantic meaning of the text.

  • Unlike LLMs (which generate text), embeddings are used for similarity search, RAG, semantic search, clustering, etc.
  • Key benefit: texts with similar meanings have vectors that are close to each other in vector space.

1OpenAI embeddings (closed source / hosted)

Uses OpenAIEmbeddings from langchain_openai. Requires an API key. Easy to use, high quality, and fast. Two main methods: .embed_query() for a single query and .embed_documents() for multiple documents.

python 
from langchain_openai import OpenAIEmbeddings
import os
from dotenv import load_dotenv

load_dotenv()

embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small",   # or "text-embedding-3-large"
    openai_api_key=os.getenv("OPENAI_API_KEY")
)

# Embed a single query
query_result = embeddings.embed_query("What is LangChain?")

# Embed multiple documents
documents = [
    "LangChain is a framework for building LLM applications.",
    "RAG stands for Retrieval Augmented Generation."
]
doc_result = embeddings.embed_documents(documents)

print("Query embedding dimension:", len(query_result))
print("Document embedding dimension:", len(doc_result[0]))

2Hugging Face embeddings (open source)

Local: uses HuggingFaceEmbeddings (downloads the model to your machine). Runs on your CPU/GPU using sentence-transformers. Example model: sentence-transformers/all-MiniLM-L6-v2. Good for privacy, offline use, and no API cost.

python 
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(
    model_name="sentence-transformers/all-MiniLM-L6-v2",  # very popular & fast
    # model_kwargs={'device': 'cuda'}   # use 'cpu' or 'cuda'
)

# Embed a single query
query_result = embeddings.embed_query("What is LangChain?")

# Embed multiple documents
documents = [
    "LangChain is a framework for building LLM applications.",
    "RAG stands for Retrieval Augmented Generation."
]
doc_result = embeddings.embed_documents(documents)

print("Query embedding dimension:", len(query_result))
print("Document embedding dimension:", len(doc_result[0]))
02 · Models

Document similarity

Document similarity is a technique to find how semantically similar two or more pieces of text are, using their embeddings.

  • Embeddings convert text into vectors.
  • We compare these vectors using cosine similarity (the most common method).
  • Higher cosine score (closer to 1) = more similar documents.
  • This is the foundation for RAG, semantic search, and retrieval systems.
python — document similarity with cosine similarity 
from langchain_huggingface import HuggingFaceEmbeddings
import numpy as np
from sklearn.metrics.pairwise import cosine_similarity

# Load embedding model
embeddings = HuggingFaceEmbeddings(
    model_name="sentence-transformers/all-MiniLM-L6-v2"
)

# Sample documents
documents = [
    "LangChain is a framework for building applications with LLMs.",
    "LangChain helps in developing LLM-powered applications.",
    "Python is a popular programming language.",
    "Machine learning is a subset of artificial intelligence."
]

# Embed documents
doc_embeddings = embeddings.embed_documents(documents)

# Query
query = "What is LangChain?"
query_embedding = embeddings.embed_query(query)

# Calculate similarity
similarities = cosine_similarity([query_embedding], doc_embeddings)[0]

# Show results
for i, score in enumerate(similarities):
    print(f"Document {i+1}: Score = {score:.4f} → {documents[i]}")
Output interpretation: the document with the highest score is the most similar to the query.
02 · Models

Temperature

Temperature is a key hyperparameter in LLMs that controls the randomness (or creativity) of the generated output.

Simple explanation

  • Low temperature (e.g., 0.0 to 0.3): more deterministic/focused. The model picks the most probable words, giving consistent, repetitive, or "safe" answers. Ideal for factual tasks, code generation, or math.
  • Temperature = 1.0: default behavior — uses the model's natural probability distribution.
  • High temperature (e.g., 0.7 to 1.5+): more creative/random. The model is more likely to pick less probable words, leading to diverse, surprising, or even hallucinated outputs. Good for storytelling, brainstorming, or poetry.

In LangChain you set it like this:

python 
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o", temperature=0.7)

How it works internally (technical details)

1

Model outputs logits

The LLM produces logits (raw scores) for every possible next token in its vocabulary. Higher logit = higher confidence for that token.

2

Softmax function (converts logits to probabilities)

Normally: P_i = e^z_i / Σ_j e^z_j

3

Temperature scaling

Before applying softmax, divide the logits by the temperature value T: P_i = e^(z_i/T) / Σ_j e^(z_j/T)

  • T < 1 (low temperature): dividing by a small number makes the differences between logits larger → the highest logit dominates even more → peaky distribution (very confident, deterministic).
  • T > 1 (high temperature): dividing by a large number shrinks the differences → distribution becomes flatter → even lower-probability tokens get a decent chance → more random/creative.

Prompts are the input instructions or queries that you give to a model to guide its output.

The content in the prompt can be: text, image, video, sound, and more.

There are two types of prompts in LangChain:

A prompt that is written directly as a string. It does not accept any input variables.

A prompt that contains placeholders (variables) which can be replaced with actual values when running the code.

03 · Prompts & Structured Output

Dynamic prompts

We can create dynamic prompts with the ChatPromptTemplate class from the langchain_core library.

Most popular methods in ChatPromptTemplate

  • from_messages([...]) — build a prompt from a list of (role, content) pairs.
  • from_template("...") — build a prompt from a single string template.
  • format(**kwargs) — fill placeholders and return a string prompt.
  • format_messages(**kwargs) — fill placeholders and return a list of structured messages (system/human/ai objects).
  • partial(**kwargs) — pre-fill some variables so you don't need to pass them every time.
  • __call__(**kwargs) — shortcut for format_messages.
python 
from langchain_core.prompts import ChatPromptTemplate
from langchain_groq import ChatGroq
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful {domain} expert."),
    ("human", "Explain {topic} in {level} language."),
    ("ai", "Sure, I can help with that."),
    ("human", "{question}")
])

prompt_value = prompt.format(
    domain="data science",
    topic="decision trees",
    level="simple",
    question="Can you give me a real-world example?"
)
llm = ChatGroq(
    model="openai/gpt-oss-120b",
    temperature=0.7
)
response = llm.invoke(prompt_value)
print(response.content)

Saving & loading templates

Instead of writing the same prompt again and again in different files, create a PromptTemplate once, save it as JSON, and load it wherever needed. This makes code clean, maintainable, and scalable.

save template as JSON 
prompt.save("research_prompt.json")
load template in any program 
from langchain.prompts import load_prompt
prompt = load_prompt("research_prompt.json")
Why use PromptTemplate instead of plain f-strings? default validation, reusability, and the LangChain ecosystem.
03 · Prompts & Structured Output

MessagesPlaceholder

MessagesPlaceholder is a special component in ChatPromptTemplate that acts as a dynamic placeholder for a list of messages. It lets you insert conversation history (or any list of previous messages) into your prompt at runtime.

Why do we need it?

  • Chatbots need to remember past conversation.
  • You cannot hardcode history in the template because it keeps changing.
  • MessagesPlaceholder solves this by acting as a slot where you can inject previous messages dynamically.

Simple code example

python 
from langchain.prompts import ChatPromptTemplate
from langchain.prompts import MessagesPlaceholder
from langchain_core.messages import HumanMessage, AIMessage

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful AI assistant."),
    MessagesPlaceholder(variable_name="chat_history"),   # this is the placeholder
    ("human", "{input}")
])

When you run it:

python 
chat_history = [
    HumanMessage(content="Hi, how are you?"),
    AIMessage(content="I'm doing great! How can I help you today?"),
    HumanMessage(content="What is LangChain?")
]

final_messages = prompt.format_messages(
    chat_history=chat_history,      # inject history here
    input="Tell me more about it"
)

Key points

FeatureDescription
PurposeInsert dynamic list of messages (especially chat history)
variable_nameRequired — this is how you pass the messages later
Input TypeList of BaseMessage objects (HumanMessage, AIMessage, etc.)
LocationUsually placed after the System Message and before the latest user input
Best Use CaseBuilding chatbots with memory

Real-world flow

  1. System Message → sets behavior
  2. MessagesPlaceholder → past conversation history
  3. Latest Human Message → current user question

This structure helps the model understand the full context of the conversation.

03 · Prompts & Structured Output

Structured output

Normally an LLM returns plain text — unstructured output. Structured output forces the model to return data in a well-defined format (most commonly JSON, or Python objects like dictionaries or Pydantic models), making output predictable, easy to parse, validate, and use programmatically.

Why do we need structured output?

  • LLMs are great at talking to humans but poor at directly talking to machines/systems.
  • Structured output turns the LLM into a reliable data processor.
  • It enables seamless integration with other parts of your application.

Real-world use cases

  • Data extraction (e.g., resume parsing for job portals): upload resumes → extract text → send to LLM → get structured JSON (name, experience, education, last company, etc.) → directly insert into a database. No manual parsing needed.
  • Review analysis / sentiment extraction (e.g., e-commerce sites): take product reviews → ask the LLM to extract topics (battery, display, processor), pros and cons, overall sentiment → return structured data → store in a DB or expose via API.
  • Building agents: agents need tools that expect specific inputs like numbers, not natural language. Structured output helps the agent reliably extract parameters (e.g., "square root of 2" → extract the number 2) before calling the tool.

Ways to get structured output

Models that support structured output

Use with_structured_output() directly.

Models that cannot generate structured output

Use an output parser to get structured output from these models.

with_structured_output — three ways

TypedDict Pydantic JSON

ATypedDict

Simplest way for basic structures. Define a class that inherits from TypedDict. Add descriptions using Annotated for better guidance to the model.

python 
from langchain_groq import ChatGroq
from dotenv import load_dotenv
from typing import TypedDict, Annotated, Literal
load_dotenv()

class out1(TypedDict):
    title: Annotated[str, "This is the title of the para"]
    sentiment: Annotated[Literal["pos","neg"], "This is the sentiment of the para like negative, positive and neutral"]

model = ChatGroq(model="openai/gpt-oss-120b", temperature=1.0)

s_model = model.with_structured_output(out1)

resp1 = s_model.invoke(
    "The 2006 Football League Championship play-off final was an association football match played on 21 May 2006 at the Millennium Stadium in Cardiff, Wales, between Leeds United and Watford. The match was to determine the third and final team to gain promotion from the Football League Championship, the second tier of English football, to the FA Premiership."
)
print(resp1)
Output: {'sentiment': 'pos', 'title': '2006 Championship Play-off Final: Leeds United vs Watford'}

BPydantic

Pydantic is a Python library used for data validation and data parsing. It ensures the data you work with is correct, structured, and type-safe.

  • Define a class that inherits from BaseModel.
  • Add fields with types and descriptions using Field(...).
  • Benefits: automatic validation, type hints, default values, and rich error handling.
  • Returns a Pydantic object (which you can easily convert to a dict if needed).

Pydantic is preferred in most real projects because of its robustness.

python 
from pydantic import BaseModel, Field
from typing import Optional, List
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv

load_dotenv()

# Define schema
class Person(BaseModel):
    name: str = Field(description="Full name of the person")
    age: int = Field(description="Age of the person")
    occupation: str = Field(description="Current profession")
    email: Optional[str] = Field(default=None, description="Email address")
    skills: List[str] = Field(description="List of skills")

# Initialize
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
structured_llm = llm.with_structured_output(Person)

# Test
text = """
My name is Priya Mehta, 26 years old. I work as a Machine Learning Engineer at Microsoft.
Skills: Python, Deep Learning, LangChain. Contact: priya.mehta@outlook.com
"""

result = structured_llm.invoke(text)
print(result)
Output: name='Priya Mehta' age=26 occupation='Machine Learning Engineer' email='priya.mehta@outlook.com' skills=['Python', 'Deep Learning', 'LangChain']

CJSON

You can also pass a raw JSON schema dictionary. Some models support native JSON mode (via provider APIs like OpenAI). LangChain handles the underlying prompting and parsing for you.

python 
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

json_schema = {
    "title": "Person",
    "type": "object",
    "properties": {
        "name": {"type": "string", "description": "Full name"},
        "age": {"type": "integer", "description": "Age"},
        "occupation": {"type": "string", "description": "Current job"},
        "email": {"type": "string", "description": "Email address"},
        "skills": {
            "type": "array",
            "items": {"type": "string"},
            "description": "List of skills"
        }
    },
    "required": ["name", "age", "occupation", "skills"]
}

structured_llm = llm.with_structured_output(json_schema)

result = structured_llm.invoke("My name is Rahul Sharma, 28 years old...")
print(result)   # Returns dict
03 · Prompts & Structured Output

Output parsers

Output parsers convert a raw LLM response into structured formats like Pydantic models, JSON, or CSV. They can be used with models that generate structured output and models that cannot. The four most useful types are StrOutputParser, JsonOutputParser, PydanticOutputParser, and StructuredOutputParser.

1StrOutputParser

A class in langchain_core.output_parsers that takes the output of an LLM as input and returns a string as output.

python 
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import PromptTemplate
from langchain_ollama import ChatOllama

# defining everything
model = ChatOllama(model="gemma3:270m")
parser = StrOutputParser()
template = PromptTemplate.from_template(
    "create a 5 line summary about {topic}"
)
inp = input("Enter the topic name : ")

# chain
chain1 = template | model | parser
resp = chain1.invoke({"topic": inp})
print(resp)

2JsonOutputParser

A class in langchain_core.output_parsers that takes the output of an LLM as input and returns a JSON dictionary as output.

python 
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import JsonOutputParser
from langchain_ollama import ChatOllama

# creation
parser = JsonOutputParser()
template = PromptTemplate.from_template("give name,age and city of a fictional person . /n {format_instructions}").partial(format_instructions=parser.get_format_instructions())
llm = ChatOllama(model="gemma3:270m")
resp = template | llm | parser

# testing
ans = resp.invoke({})
print(ans)
The biggest drawback of JsonOutputParser is it does not enforce schema.

3StructuredOutputParser

A class in langchain.output_parsers that takes the output of an LLM as input and returns a JSON dictionary based on a defined schema. It is the upgraded version of JsonOutputParser — you can define a schema.

python 
from langchain_classic.output_parsers import StructuredOutputParser, ResponseSchema
from langchain_ollama import ChatOllama
from langchain_core.prompts import PromptTemplate

# creation
model = ChatOllama(model="llama3.2:1b")
schema = [
    ResponseSchema(name="name", description="name of the person"),
    ResponseSchema(name="age", description="age of the person"),
    ResponseSchema(name="city", description="city of the person")
]
parser = StructuredOutputParser.from_response_schemas(schema)
template = PromptTemplate.from_template("Give details of an imaginary person who is living in {state} \n {format_instructions}").partial(format_instructions=parser.get_format_instructions())

# invoking and printing
print(f"original template : {template}")
print(f"original schema : {schema}")
chain = template | model | parser
state1 = input("Enter the preferred state : ")
resp = chain.invoke({"state": state1})
print(resp)
The main drawback is it doesn't provide any data validation.

4PydanticOutputParser

PydanticOutputParser is a class in langchain_core.output_parsers that parses LLM responses into a structured Pydantic model. Unlike JsonOutputParser or StructuredOutputParser, it leverages Pydantic's data validation and type enforcement. If the LLM produces data that doesn't match the model, Pydantic raises a validation error — ensuring reliable, strongly-typed data.

python 
from typing import List
from pydantic import BaseModel, Field
from langchain_core.output_parsers import PydanticOutputParser
from langchain_core.prompts import PromptTemplate
from langchain_ollama import ChatOllama

# 1. Define the Pydantic schema
class Person(BaseModel):
    name: str = Field(description="Name of the person")
    age: int = Field(description="Age of the person")
    hobbies: List[str] = Field(description="List of hobbies")

# 2. Setup parser and model
parser = PydanticOutputParser(pydantic_object=Person)
model = ChatOllama(model="gemma3:270m")

# 3. Create prompt with format instructions
template = PromptTemplate.from_template(
    "Provide details for a fictional character. \n{format_instructions}\n"
).partial(format_instructions=parser.get_format_instructions())

# 4. Invoke the chain
chain = template | model | parser

Runnables & LCEL

Interview-ready notes on Runnables & LCEL in LangChain.

1What are Runnables?

Runnables are the foundational building blocks of modern LangChain. Any component that can accept an input, process it, and return an output follows the Runnable interface — including prompt templates, LLMs, output parsers, retrievers, tools, and even complete chains.

The main idea is a standardized, unified interface so all LangChain components can be composed together like Lego blocks. This makes building complex LLM applications more modular, flexible, and maintainable.

2Why were Runnables introduced?

Traditional chains in early LangChain were simple but rigid. They worked for basic sequences but struggled with parallel processing, conditional logic, selective data passing, debugging, and scaling. Runnables solve these issues by providing a powerful composition system — the basis of LCEL (LangChain Expression Language) — making LangChain far more production-ready.

3Core features of Runnables

Every Runnable supports consistent methods:

  • .invoke(input) — synchronous execution
  • .ainvoke(input) — asynchronous execution
  • .batch(inputs) — process multiple inputs in one go
  • .stream(input) — real-time streaming support
The most powerful feature is the pipe operator (|), which creates seamless sequences where the output of one component automatically becomes the input for the next.

4Major types of Runnables

RunnablePurpose
RunnableSequenceConnects multiple components in a linear flow — the backbone of most chains. e.g. chain = prompt | llm | output_parser
RunnableParallelRuns several components at the same time (concurrently) — useful when fetching data from multiple sources or processing independent branches.
RunnablePassthroughPasses input data forward without modification — commonly paired with RunnableParallel to preserve the original information (like the user's question) while adding new processed data (like retrieved documents).
RunnableLambdaWraps any custom Python function into a Runnable — for custom logic, data transformations, or formatting.
RunnableBranchEnables conditional routing — the flow can branch into different paths based on logic (e.g., query type).

from langchain_core.runnables import RunnableLambda

def add(values):
    return values["a"] + values["b"]

run_add = RunnableLambda(add)
resp = run_add.invoke({"a": 10, "b": 20})
print(resp)

    return values[0] + values[1]

5LCEL — LangChain Expression Language

LCEL is the expression language built on top of Runnables. It composes complex chains using simple, declarative syntax (mainly the | operator along with parallel and other utilities).

  • Highly readable and Pythonic code.
  • Automatic handling of input/output schemas between components.
  • Excellent support for parallelism, streaming, async, and batching.
  • Forms the foundation for advanced frameworks like LangGraph.
In short: Runnables + LCEL = the modern way to build LLM applications in LangChain.

6Most important patterns (high-impact for interviews)

Custom document loaders

LangChain has many built-in loaders, but you might need a custom one when working with proprietary or unusual file formats (e.g., .log, .xml, custom APIs), needing specific preprocessing logic during loading, integrating with internal databases/APIs not covered by default loaders, or extracting data from complex structures (e.g., nested JSON, specialized HTML).

To create a custom loader, subclass BaseLoader and implement two key methods:

  1. lazy_load() — a generator that yields Document objects one by one (memory efficient).
  2. load() — usually just calls list(self.lazy_load()) to return all documents at once.
python — basic template 
from langchain_core.document_loaders import BaseLoader
from langchain_core.documents import Document
from typing import Iterator

class MyCustomLoader(BaseLoader):
    def __init__(self, source_path: str):
        self.source_path = source_path

    def lazy_load(self) -> Iterator[Document]:
        # Your logic to read and parse the file
        with open(self.source_path, 'r') as f:
            for line in f:
                yield Document(
                    page_content=line.strip(),
                    metadata={"source": self.source_path}
                )

When yielding documents, always include:

  • page_content (str) — the actual text content extracted.
  • metadata (dict) — extra info like source file, page number, date, author, etc.

Text splitters

Text splitters break down large, unstructured text documents into smaller, manageable pieces called chunks or documents.

Why is text splitting needed?

  • Context window limitations: LLMs have a maximum amount of text they can process at once. Exceeding this limit causes errors or loss of information.
  • Chunking for RAG: splitting text into smaller chunks allows for more precise retrieval than searching through entire documents.

Key parameters: chunk size & overlap

  • Chunk size (chunk_size): the maximum length (in characters or tokens) of a chunk.
  • Chunk overlap (chunk_overlap): the amount of text shared between consecutive chunks. This helps maintain context when a piece of information is split across a boundary.
bash — basic installation 
pip install -qU langchain-text-splitters

Text splitting fundamentals

The core challenge is balancing trade-offs:

  • Large chunks: preserve more context but risk irrelevant information being included (lower precision) and may not fit in the context window.
  • Small chunks: are more focused and precise but risk losing surrounding context (lower recall).
  • Overlap: a crucial strategy to prevent context from being lost at the breakpoints between chunks.

3Length-based text splitting

The simplest category — splitting text purely based on a size limit.

A. Character-based splitting (CharacterTextSplitter)

  • How it works: splits text based on a fixed number of characters.
  • Separator: you can specify a separator (e.g., \n\n). It will try to split at the separator, but if a chunk still exceeds chunk_size, it will cut mid-text.
  • Best for: simple, unstructured plain text where boundaries are unimportant.
python 
from langchain_text_splitters import CharacterTextSplitter

# Basic character-based splitter
char_splitter = CharacterTextSplitter(
    chunk_size=200,      # Maximum chunk size in characters
    chunk_overlap=0,     # No overlap between chunks
    separator=" "        # Split on spaces
)

text = "This is a very long piece of text that we need to split into smaller chunks for processing by an LLM."
chunks = char_splitter.split_text(text)
print(chunks)
# Output: ['This is a very long piece of text that we need to split into smaller',
#          'chunks for processing by an LLM.']

B. Token-based splitting (TokenTextSplitter)

  • How it works: splits text based on the number of tokens — how LLMs actually "see" text. More accurate for respecting model limits.
  • Token counting: can use different tokenizers (e.g., cl100k_base for GPT-4) to match your LLM.
python 
from langchain_text_splitters import TokenTextSplitter

# Token-based splitter (using tiktoken encoder)
token_splitter = TokenTextSplitter(
    chunk_size=50,       # Maximum tokens per chunk
    chunk_overlap=10     # Overlap of 10 tokens
)

text = "This is a long document that needs to be split based on token count rather than characters."
chunks = token_splitter.split_text(text)

4Text-structure-based splitting (recursive) — RECOMMENDED

The recommended starting point for most use cases.

RecursiveCharacterTextSplitter

  • How it works: uses a hierarchical list of separators (e.g., ["\n\n", "\n", " ", ""]). It recursively tries to split on the largest separator first (paragraphs), then moves to the next (sentences), and finally to individual characters to ensure chunks are under the size limit.
  • Advantages: it intelligently preserves semantic units like paragraphs and sentences, creating much more coherent chunks than fixed-length splitting.
python 
from langchain_text_splitters import RecursiveCharacterTextSplitter

# Default recursive splitter (recommended for most use cases)
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # Maximum size of chunks
    chunk_overlap=50,    # Amount of overlap between chunks
    length_function=len,
    separators=["\n\n", "\n", " ", ""]  # Hierarchical separators
)

# Load a document
with open("document.txt") as f:
    document = f.read()

# Split into chunks
chunks = text_splitter.split_text(document)

# Or create LangChain Document objects directly
documents = text_splitter.create_documents([document])
print(documents[0].page_content)

Understanding separators

python — custom separators for better control 
text_splitter = RecursiveCharacterTextSplitter(
    separators=[
        "\n\n",    # Paragraphs - highest priority

6Semantic meaning-based splitting — ADVANCED

The most advanced technique. Instead of fixed lengths or separators, it splits text at "semantic breakpoints" where the topic changes.

SemanticChunker

  1. Break into sentences: the text is first split into individual sentences.
  2. Generate embeddings: each sentence is converted into a numerical vector capturing its meaning.
  3. Calculate differences: it measures the semantic distance (dissimilarity) between consecutive sentences.
  4. Identify breakpoints: sentences are grouped until the difference exceeds a threshold, indicating a shift in topic.

Best for advanced RAG systems where retrieval quality is paramount.

    embeddings=embedding_model,

    breakpoint_threshold_amount=95  # Threshold percentile
)

text = """

Machine learning algorithms can now recognize patterns in data.
The weather today is sunny and warm.
It's a perfect day for a picnic in the park.
Back to AI topics: Neural networks are inspired by the human brain.
Deep learning has achieved remarkable results in image recognition.
"""

semantic_chunks = semantic_splitter.split_text(text)

# Each chunk should contain semantically related sentences
for i, chunk in enumerate(semantic_chunks):
    print(f"Chunk {i+1}: {chunk[:100]}...\n")

Vector stores

A vector store is a specialized system (or database) designed to store and retrieve data represented as numerical vectors (embeddings). These embeddings capture the semantic meaning of text, images, or other data in high-dimensional space.

Key features of vector stores

  • Storage: holds vectors plus associated metadata (source, author, timestamps, etc.). Can be in-memory (fast for small data) or persistent (disk/cloud).
  • Similarity search: finds vectors most similar to a query vector using metrics like cosine similarity, dot product, or Euclidean distance.
  • Indexing: uses efficient data structures (e.g., Approximate Nearest Neighbors — ANN) for fast searches on millions of vectors instead of slow linear scans.
  • CRUD operations: create (add), read (search), update, and delete vectors/documents.

Why do we need vector stores?

  • Enable semantic search (meaning-based) rather than simple keyword matching.
  • Core component of RAG: retrieve relevant external context to ground LLM responses and reduce hallucinations.
  • Applications: document Q&A systems, intelligent chatbots, recommender systems, semantic search engines, knowledge bases, image/multimedia search.

Note: a vector database is essentially an advanced vector store with robust database functionalities.

Chroma vector store

Chroma is highlighted for its simplicity and is beginner-friendly.

Chroma hierarchy

Tenant → Top level Database → Under tenant Collection → Under database (where documents live) Documents → Individual entries with embeddings and metadata
python 
from langchain_community.vectorstores import Chroma
from langchain_huggingface import HuggingFaceEmbeddings
from langchain.schema import Document

# Initialize embeddings
embeddings = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2")

# Sample documents
docs = [
    Document(page_content="Content of document 1...", metadata={"source": "file1.pdf", "page": 1}),
    # ... more documents
]

# Create vector store (persistent)
vector_store = Chroma.from_documents(
    documents=docs,
    embedding=embeddings,
    persist_directory="./chroma_db"  # Saves to disk
)

# Similarity search
results = vector_store.similarity_search("Your user query here", k=4)

for doc in results:
    print(doc.page_content)
    print(doc.metadata)

Other operations

  • Adding more documents: vector_store.add_documents(new_docs)
  • Persistence and reloading.
  • Metadata filtering: e.g., filter={"source": "file1.pdf"}

Best practices & key takeaways

  • Always chunk documents properly before embedding (use recursive character text splitters, etc.).
  • Choose the right store: local/dev — FAISS or Chroma; production — Pinecone, Weaviate, etc.
  • Use metadata filtering for better precision.
  • Handle persistence carefully for reuse across sessions.
  • Monitor embedding model quality — it greatly affects search relevance.
  • Combine with LangChain retrievers for clean RAG pipelines: vector_store.as_retriever(search_kwargs={"k": 5}).

Wikipedia retriever

Used to fetch relevant documents from Wikipedia — it uses the Wikipedia API under the hood. You give it a query (e.g., "Albert Einstein"), it sends the query to Wikipedia's API, retrieves the most relevant articles, and returns them as LangChain Document objects.

python 
from langchain_community.retrievers import WikipediaRetriever
retriever = WikipediaRetriever()
resp = retriever.invoke("prabhas")
print(resp[0].page_content)

If you get an error and no response from the Wikipedia API, the API may be restricting you. In that case add the code below before retriever initialization. Wikimedia requires all API clients to provide a unique identifier in the User-Agent header so they can track usage and prevent abusive automated scraping. Giving your application a descriptive User-Agent lifts the rate-limit block, allowing the API to return valid JSON again.

python 
import wikipedia
wikipedia.set_user_agent("MyApp/1.0 (langchain_bot)")  # always replace langchain_bot with an email so that if your app accidentally hits a loop or causes high traffic, the Wikimedia team can reach out instead of flat-out blocking your IP address.

Maximal Marginal Relevance (MMR)

MMR is a retrieval technique that retrieves documents relevant to the query but diverse from each other — avoiding fetching documents that are very similar to each other.

The lambda value ranges from 0–1: 0 being fully diverse, 1 being fully similar. In LangChain we define lambda as a parameter in search_kwargs called lambda_mult.

python 
from langchain_core.documents import Document
from langchain_ollama import OllamaEmbeddings
from langchain_chroma import Chroma

# 1. Create documents
documents = [
    Document(page_content="Kafka provides high scalability for streaming applications."),
    Document(page_content="Kafka offers fault tolerance through replication."),
    Document(page_content="Kafka supports real-time data processing."),
    Document(page_content="Kafka scales horizontally across multiple brokers."),
    Document(page_content="Kafka is commonly used in ETL and data pipelines.")
]

# 2. Create embeddings model
embeddings = OllamaEmbeddings(
    model="nomic-embed-text"
)

# 3. Store documents in Chroma
vectorstore = Chroma.from_documents(
    documents=documents,
    embedding=embeddings
)

# 4. Create MMR retriever
retriever = vectorstore.as_retriever(
    search_type="mmr",
    search_kwargs={
        "k": 3,
        "fetch_k": 5,
        "lambda_mult": 0.7
    }
)

# 5. Query
query = "What are the benefits of Kafka?"

results = retriever.invoke(query)

# 6. Print results
for doc in results:
    print(doc.page_content)

Multi query retriever

MultiQueryRetriever (MQR) is a LangChain retriever that uses an LLM to generate multiple variations of the user's query and retrieves documents for each variation. We use it because a single query may miss relevant documents because of wording differences.

For the user query "What are the benefits of Kafka?", it might generate:

What advantages does Kafka provide? Why is Kafka used in data pipelines? What Kafka features improve scalability? How does Kafka support real-time processing?
flowchart LR A[User Query] --> B[Generate Multiple Queries] B --> C[Vector Search] C --> D[Merge and Deduplicate] D --> E[LLM Answer]
python 
from langchain_chroma import Chroma
from langchain_ollama import ChatOllama, OllamaEmbeddings
from langchain_classic.retrievers import MultiQueryRetriever

# Embeddings
embeddings = OllamaEmbeddings(
    model="llama3:8b"
)
# Vector Store
vectorstore = Chroma.from_texts(
    [
        "Kafka provides high scalability.",
        "Kafka supports real-time stream processing.",
        "Kafka offers fault tolerance through replication."
    ],
    embedding=embeddings
)

# Base Retriever
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

# LLM for query generation
llm = ChatOllama(model="llama3:8b")

# Multi Query Retriever
multi_query_retriever = MultiQueryRetriever.from_llm(
    retriever=retriever,
    llm=llm
)

# Retrieve documents
docs = multi_query_retriever.invoke(
    "What are the benefits of Kafka?"
)

for doc in docs:
    print(doc.page_content)

Contextual compression retriever

A Contextual Compression Retriever retrieves documents first and then compresses/filters the retrieved content to keep only the parts relevant to the user's query.

python 
from langchain_classic.retrievers import ContextualCompressionRetriever
from langchain_classic.retrievers.document_compressors import LLMChainExtractor
from langchain_ollama import ChatOllama
from langchain_ollama import OllamaEmbeddings
from langchain_community.vectorstores import Chroma

# Base retriever
embeddings = OllamaEmbeddings(
    model="llama3:8b"
)
# Vector Store
vectorstore = Chroma.from_texts(
    [
        "Kafka provides high scalability.",
        "Kafka supports real-time stream processing.",
        "Kafka offers fault tolerance through replication."
    ],
    embedding=embeddings
)
base_retriever = vectorstore.as_retriever()

# LLM used for compression
llm = ChatOllama(model="llama3:8b")

# Compressor
compressor = LLMChainExtractor.from_llm(llm)

# Contextual Compression Retriever
compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=base_retriever
)

docs = compression_retriever.invoke(
    "What are the benefits of Kafka?"
)

for doc in docs:
    print(doc.page_content)

06 · Retrieval Augmented Generation (RAG)

Why RAG?

Retrieval-Augmented Generation (RAG) is an AI architecture that combines a retriever (finds relevant information from external knowledge sources) and a generator (LLM) (generates the final answer using both the retrieved information and the user's query). Instead of relying only on the LLM's pre-trained knowledge, RAG lets it use external, up-to-date, domain-specific data.

Limitations of LLMs that RAG addresses

  • Hallucination — LLMs sometimes generate incorrect information confidently.
  • Knowledge cutoff — models only know what existed until their training cutoff.
  • Private data — LLMs cannot answer questions about company documents, internal PDFs, hospital records, or college notes unless these documents are provided.
06 · Retrieval Augmented Generation (RAG)

Steps in RAG

There are four steps in a RAG system.

1

Indexing

The process of creating an external knowledge base from which you will provide context to an LLM.

2

Retrieval

The process of understanding the query and retrieving the similar chunks related to the query from the external knowledge base you created.

3

Augmentation

The process of combining both the query and the context to create a useful prompt that can be sent to an LLM.

4

Generation

The final step where the LLM generates the actual response from the context and prompt sent to it.

Indexing

Indexing is the process of preparing your knowledge base so it can be efficiently searched at query time. It consists of 4 sub-steps:

  1. Document loading
  2. Chunking
  3. Embedding
  4. Storing the embeddings in a vector store
flowchart LR A[Documents] --> B[Chunking] B --> C[Embeddings] C --> D[Vector Database]

Retrieval

When the user asks a question:

  1. Convert the query into an embedding.
  2. Search the vector database.
  3. Retrieve the top-K most relevant chunks.

Advantages & limitations

Advantages

  • Reduces hallucinations
  • Uses latest information
  • Works with private documents
  • No need to retrain the models
  • Easy to update by changing documents

Limitations

  • Retrieval quality affects answer quality
  • Chunking strategy is important
  • Embedding model quality matters
  • Poor retrieval leads to poor answers

Chain vs agent — when is each right?

Chains: fixed sequence (predictable, cheap). Agents: model chooses tools/steps dynamically (flexible, costlier, needs guardrails).

Why split documents before embedding?

Embeddings have context limits and retrieval is sharper on focused chunks. Splitters balance semantic coherence vs chunk size/overlap.

Indexes chunk embeddings for similarity search so the retriever can fetch the top-k passages that ground the final answer.
